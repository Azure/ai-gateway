How Azure AI Gateway works

A 20-minute visual tour of the AI Gateway tier of Azure API Management. Follow one request through the gateway, meet models, aliases, MCP servers, policies, and identities, and pick the learning path that fits your role.

Beginner 20 min Portal Updated Oct 14, 2026
Source Edit

What you'll do

  • Describe what the AI Gateway tier does and where it sits between your apps, agents, models, and tools
  • Follow a request through authentication, policies, alias routing, the backend, and telemetry
  • Explain the difference between a backend model, an alias, and an MCP server
  • Predict which policies apply to a request and which status code a blocked request returns
  • Choose the learning path that matches your role

Before you start

No prerequisite labs. Start here.

Tracks: Portal

Every team that ships generative AI hits the same questions. Which models may we call, and with which keys? Who spent the tokens? How do we stop one agent from starving everyone else, or from calling a tool it should never touch? The AI Gateway tier of Azure API Management answers them in one place: apps and agents call one gateway, and the gateway decides who gets in, which model or tool answers, what each call may cost, and what gets recorded.

Note

The AI Gateway tier is in public preview in East US 2 and Sweden Central. The gateway itself is free during the preview. Connected services, such as Microsoft Foundry inference and Application Insights, are billed normally.

#Before you begin

This lab is a guided reading. You don't need to deploy anything.

  • If you already have a gateway, open the AI Gateway portal↗ in another tab and follow the portal tour at the end.
  • If you don't have one yet, read on. You create your first gateway in Provision your first AI gateway.

#How it works

The gateway sits on the path of every model call and every tool call. It has two faces:

  • Data plane: the runtime endpoints your code calls, at https://<gateway>.azure-api.net.
  • Control plane: the product portal at ai.gateway.azure.com↗, the az aigateway CLI extension, and the Azure Resource Manager API (Microsoft.ApiManagement/service, SKU AIGateway).
Building blockWhat it isExample
GatewayAn Azure API Management service on the AI Gateway tierhttps://<gateway>.azure-api.net
Backend modelA model at a provider, such as a Foundry deployment or an Anthropic modelgpt-4.1-mini at Microsoft Foundry
AliasThe stable, gateway-wide name clients send in the model fieldchat
MCP serverOne governed MCP endpoint that federates tools from one or more sources/default/toolservers/<server-name>/mcp
PolicyA rule on the gateway or on one asset: limits, budgets, safety, filtersToken rate limit, Cost limit
AccessHow callers authenticate: API keys or Microsoft Entra ID rolesapi-key header or Entra token
Managed identityHow the gateway authenticates to backendsFoundry User role on the Foundry account
MonitoringOpenTelemetry metrics, logs, and traces for every callApplication Insights or any OTLP endpoint

Model calls use protocols developers already know. The OpenAI-compatible base URL is https://<gateway>.azure-api.net/default/models/openai/v1 (append /responses or /chat/completions), and Anthropic Messages lives at /default/models/anthropic/v1/messages. The gateway passes requests through without translating between OpenAI and Anthropic formats, so call each model on an interface it advertises.

#Follow one request

Press Play to send a request through the gateway. Then switch scenarios to see where each policy stops a request and which status code the caller gets back.

Three rules explain almost every response you'll see in these labs:

  1. Policies run before the backend. If any applicable policy blocks a request, the gateway answers right away and never calls the backend.
  2. Each block has a predictable status. 401 for missing or invalid credentials, 403 for IP filters and cost limits (LlmCostQuotaExceeded), 429 with Retry-After for token and request rate limits, and 400 for content safety.
  3. Everything is recorded. Allowed and blocked calls both show up in Monitoring, along with the policies that affected them.

#Models and aliases

A backend model is what a provider serves. An alias is what your clients call. Microsoft Foundry imports create an alias for each model by default, and you can add more. Because clients only know the alias, you can move it to a newer or cheaper model without a code change, and the alias keeps its own policies.

You can put models from Microsoft Foundry, Azure OpenAI, OpenAI, Anthropic, AWS Bedrock, Google Vertex AI, and custom OpenAI-compatible endpoints behind aliases. You try it in Route models from several providers behind aliases.

#MCP servers and tools

Agents need tools as much as models. An MCP server on the gateway gives agents one endpoint and one credential for tools from remote MCP servers, OpenAPI specifications, built-in connectors, and Foundry Toolbox. Tool names are namespaced per source, and tool availability decides which tools clients can see and call.

#Policies and scopes

You add a policy at gateway scope, where it applies to every compatible asset including assets you add later, or to individual assets: a backend model, an alias, or an MCP server. Pick an asset below to see every policy that applies to it.

PolicyApplies toWhen it blocks
Token rate limitModels and aliases429 with Retry-After
Request rate limitModels, aliases, and MCP servers429 with Retry-After
Cost limitModels and aliases403 LlmCostQuotaExceeded
Content safetyModels, aliases, and MCP servers400
IP filterModels, aliases, and MCP servers403
Agent 365 tool threat protectionMCP serversDenies the tool call

At gateway scope, the policy type decides which assets are relevant. A gateway-scope cost limit, for example, tracks one budget across all models.

#Identities on both sides

The gateway separates who is calling from how the gateway reaches the backend. Callers use an API key or a Microsoft Entra token with one of the AI Gateway data-plane roles. The gateway uses its own managed identity, or a provider key it stores, to call backends. Callers never see backend credentials.

#Observability

The gateway emits OpenTelemetry metrics, logs, and traces for model calls, tool calls, and policy decisions. Send them to Application Insights to light up the built-in Monitoring dashboard, or to any OTLP endpoint.

#Open your gateway

#Open Monitoring

#Verify

Check your understanding before you move on.

An app sends "model": "chat". What must chat be?

A callable alias on the gateway. The model field must exactly match an alias, not a provider deployment name.

A caller exceeds a token rate limit. Is the backend called?

No. The gateway answers 429 Too Many Requests with Retry-After and never forwards the request.

You add an IP filter at gateway scope, then add a new model next week. Is the new model protected?

Yes. Gateway-scope policies apply to every compatible asset, including assets you add later.

Which credential does the gateway use to call a Microsoft Foundry model?

Its own managed identity, which needs the Foundry User role on the Foundry account. The caller's key or token is never forwarded.
