Deploy a Foundry hosted agent behind AI Gateway

Deploy your own Microsoft Agent Framework agent to Foundry Hosted Agents with azd. The agent has no model deployment and no direct tool access, so its model calls and its Microsoft Learn MCP calls go through AI Gateway with a dedicated key. Run it locally, invoke it in Foundry, and cap its tokens without changing its code.

Intermediate 40 min PortalCLICode Updated Oct 23, 2026
Source Edit

What you'll do

  • Give a hosted agent its own runtime API key, so its usage and limits stay separate from other apps
  • Wire an Agent Framework agent to the gateway's model and MCP endpoints with the right header for each
  • Run the agent locally with azd, then deploy it to Foundry Hosted Agents with azd up
  • Cap the agent's tokens with a gateway policy, without changing its code

Before you start

  • 02Publish a Foundry model and make your first call
  • 04Federate MCP tools behind one endpoint

Tracks: Portal, Azure CLI, Code

Your team wants to run an agent in Microsoft Foundry, but the platform team needs every model call and every tool call to be governed and visible in one place. In this lab you deploy a small Microsoft Agent Framework agent to Foundry Hosted Agents. Its Foundry project has no model deployments and no tool connections: the agent reaches its model and its tools only through AI Gateway, with a key of its own.

#Before you begin

  • Complete Publish a Foundry model and make your first call and Federate MCP tools behind one endpoint. The agent calls the alias from lab 02 and the learn MCP server from lab 04.
  • An Azure subscription where you can create a resource group and a Foundry resource, and assign roles, for example Owner. azd gives the agent's identity access to its Foundry project.
  • These tools:
    • Azure Developer CLI↗ (azd) 1.34.2 or later, signed in with azd auth login
    • Python 3.13 or later. With uv↗ installed, azd uses it to create the agent's virtual environment.
    • Git
  • For the Azure CLI track: the Azure CLI with the aigateway extension, signed in to the same tenant, and jq for the Bash snippets.
Warning

azd up creates a Foundry resource, and the hosted agent and its model calls are billable. Run Clean up when you're done.

#How it works

The agent lives in infra/↗, a complete azd project:

FileWhat it does
infra/azure.yaml↗Declares a Foundry project with no model deployments, and the hosted agent gateway-agent: Python 3.13, code deploy, 0.5 CPU, 1 GiB, Responses protocol
infra/src/gateway-agent/main.py↗The agent: one model client and one MCP tool, both pointing at the gateway
infra/src/gateway-agent/requirements.txt↗Pinned dependencies, compiled from requirements.in. Foundry builds the agent from this file.

The agent has two outbound paths, and both end at AI Gateway:

  • Model. An OpenAIChatClient points at the gateway's model endpoint, /default/models/openai/v1/, and sends your lab 02 alias as model. The runtime key is the SDK's API key, so it travels as Authorization: Bearer. The model endpoint accepts a runtime key either that way or in an api-key header.
  • Tools. An MCPStreamableHTTPTool points at the gateway's /default/toolservers/learn/mcp endpoint with the same key in the api-key header. The MCP endpoint accepts keys only in that header: a bearer token there must be a Microsoft Entra token.
Important

Send a key in one header only. If a request carries both api-key and Authorization, the gateway rejects it with 400 and "Specify either an API key or an Authorization header, not both". Older samples set a placeholder API key and add an api-key header, which the OpenAI SDK turns into exactly that request.

PieceName in this labOwner
Model aliasYour alias from lab 02, in AI_GATEWAY_MODELAI Gateway

Foundry runs the agent. AI Gateway decides what the agent may call, counts its tokens, and records every call.

#Give the agent its own key

A dedicated key makes the agent a separate caller identity: its token limits, cost limits, and Monitoring data don't mix with other apps. Pick one track.

Choose your track
1

#Create the key

  1. In the AI Gateway portal↗, open your gateway and select Access›Keys.
  2. Select Create API key.
  3. In Key name, enter hosted-agent, and select Create.
  4. The API key created successfully dialog shows the value. Select Copy & done.
2

#Load the values in your shell

Paste the key without echoing it, then set the gateway URL from the gateway's Overview page and the alias from lab 02:

read -rsp "hosted-agent key: " AI_GATEWAY_API_KEY && export AI_GATEWAY_API_KEY && echo
export AI_GATEWAY_URL="https://<gateway>.<region>-01.ai.gateway.azure.com"
export AI_GATEWAY_MODEL="<model-alias>"    # the alias from lab 02
$env:AI_GATEWAY_API_KEY = Read-Host "hosted-agent key" -MaskInput
$env:AI_GATEWAY_URL = "https://<gateway>.<region>-01.ai.gateway.azure.com"
$env:AI_GATEWAY_MODEL = "<model-alias>"    # the alias from lab 02

#Create the key and load its value

api-key create returns metadata only. list-secrets reads the value straight into a variable, so it never appears on screen.

az aigateway api-key create -g "$RG" --gateway-name "$GATEWAY" -n hosted-agent --display-name hosted-agent -o none
export AI_GATEWAY_API_KEY="$(az aigateway api-key list-secrets -g "$RG" --gateway-name "$GATEWAY" -n hosted-agent \
  --query primaryKey -o tsv)"
az aigateway api-key create -g $RG --gateway-name $GATEWAY -n hosted-agent --display-name hosted-agent -o none
$env:AI_GATEWAY_API_KEY = az aigateway api-key list-secrets -g $RG --gateway-name $GATEWAY -n hosted-agent `
  --query primaryKey -o tsv
Checkpoint

Access›Keys lists hosted-agent as active, and your shell has AI_GATEWAY_URL, AI_GATEWAY_MODEL, and AI_GATEWAY_API_KEY.

#Configure the azd project

1

#Get the lab files

Clone the labs repo if you haven't yet. Then move into the lab's infra folder and install the Foundry extensions for azd:

Bash
cd ~/ai-gateway/labs/16-foundry-hosted-agent/infra
azd ext install microsoft.foundry

microsoft.foundry installs the Foundry extensions for azd, including azure.ai.agents, which adds the azd ai agent commands.

2

#Create an azd environment

The environment name also names the resource group, rg-<env>, and the Foundry project. Choose a region where Foundry Hosted Agents are available, for example eastus2.

Bash
azd env new aigw-lab16 --location eastus2
3

#Pass the gateway settings to the agent

azure.yaml↗ maps four azd environment values to the agent's environment variables:

YAML
env:
  AI_GATEWAY_URL: ${AI_GATEWAY_URL}
  AI_GATEWAY_MODEL: ${AI_GATEWAY_MODEL}
  AI_GATEWAY_API_KEY: ${AI_GATEWAY_API_KEY}
  AI_GATEWAY_MCP_SERVER: ${AI_GATEWAY_MCP_SERVER}

Set them from your shell:

azd env set AI_GATEWAY_URL "$AI_GATEWAY_URL"
azd env set AI_GATEWAY_MODEL "$AI_GATEWAY_MODEL"
azd env set AI_GATEWAY_API_KEY "$AI_GATEWAY_API_KEY"
azd env set AI_GATEWAY_MCP_SERVER learn
azd env set AI_GATEWAY_URL $env:AI_GATEWAY_URL
azd env set AI_GATEWAY_MODEL $env:AI_GATEWAY_MODEL
azd env set AI_GATEWAY_API_KEY $env:AI_GATEWAY_API_KEY
azd env set AI_GATEWAY_MCP_SERVER learn

azd keeps the values in .azure/aigw-lab16/.env, which Git ignores, and passes them to the agent locally and in Foundry. Anyone who can read the agent's definition in Foundry can also read the key; see Go further for keyless options.

#Read the agent

main.py↗ is the whole agent. The model client and the MCP tool are the only places it talks to the network, and both point at the gateway:

Python
client = OpenAIChatClient(
    model=model,
    base_url=f"{gateway_url}/default/models/openai/v1/",
    api_key=api_key,
)

tools = MCPStreamableHTTPTool(
    name="gateway-tools",
    url=f"{gateway_url}/default/toolservers/{mcp_server}/mcp",
    static_headers={"api-key": api_key},
    approval_mode="never_require",
    load_prompts=False,
    request_timeout=60,
)

ResponsesHostServer serves the agent on the Responses protocol at port 8088, the same way locally and in Foundry. The agent sets store to false on its model calls, because the hosting server already keeps the conversation history. Tool approval is off because the Learn tools are read-only.

infra/src/gateway-agent/main.pyGitHub
"""A Foundry hosted agent whose model calls and MCP tool calls both go through AI Gateway.

The agent has no Foundry model deployment and no direct route to a tool. It calls the gateway's
OpenAI-compatible model endpoint with an alias, and the gateway's MCP endpoint for one MCP server,
both with its own gateway API key.

Run it locally with `azd ai agent run`, which reads the values from the azd environment. To run it without azd,
copy .env.example to .env, install requirements.txt in a virtual environment, and run `python main.py`.
"""

import asyncio
import os

from agent_framework import Agent, MCPStreamableHTTPTool
from agent_framework.openai import OpenAIChatClient
from agent_framework_foundry_hosting import ResponsesHostServer
from dotenv import load_dotenv

load_dotenv()

INSTRUCTIONS = """
You answer questions about Microsoft and Azure technologies.
- Search the Microsoft Learn tools before you answer, and cite the URLs you used.
- If the tools don't cover the question, say so instead of guessing.
- Keep answers under 150 words.
"""


def required(name: str) -> str:
    value = os.environ.get(name, "").strip()
    if not value:
        raise RuntimeError(f"Set {name}. With azd, run: azd env set {name} <value>")
    return value


async def main() -> None:
    gateway_url = required("AI_GATEWAY_URL").rstrip("/")
    api_key = required("AI_GATEWAY_API_KEY")
    model = required("AI_GATEWAY_MODEL")
    mcp_server = os.environ.get("AI_GATEWAY_MCP_SERVER", "").strip() or "learn"

    # The model endpoint accepts the key as the SDK's bearer token. Don't add an api-key header too:
    # the gateway rejects a request that has both.
    client = OpenAIChatClient(
        model=model,
        base_url=f"{gateway_url}/default/models/openai/v1/",
        api_key=api_key,
    )

    # The MCP endpoint takes the key only in the api-key header.
    tools = MCPStreamableHTTPTool(
        name="gateway-tools",
        url=f"{gateway_url}/default/toolservers/{mcp_server}/mcp",
        static_headers={"api-key": api_key},
        approval_mode="never_require",
        load_prompts=False,
        request_timeout=60,
    )

    async with Agent(
        client=client,
        name="gateway-docs-agent",
        instructions=INSTRUCTIONS,
        tools=tools,
        # Foundry keeps the conversation history, so the model call doesn't need to store it.
        default_options={"store": False},
    ) as agent:
        await ResponsesHostServer(agent).run_async()


if __name__ == "__main__":
    asyncio.run(main())

On GitHub, open main.py↗ and azure.yaml↗.

#Run the agent locally

1

#Start the agent

From the infra folder:

Bash
azd ai agent run

azd creates a virtual environment, installs requirements.txt, starts the agent on http://localhost:8088, and opens Agent Inspector, where you can chat with the agent and see its tool calls. Add --no-client to skip Agent Inspector.

2

#Ask a question

In a second terminal, from the same folder:

Bash
azd ai agent invoke --local "Which Learn page explains Azure API Management key concepts? One sentence and the URL."

Expected output: an answer that cites a learn.microsoft.com URL, for example:

Text
[local] The Learn page "What is Azure API Management?" explains its key concepts.
URL: https://learn.microsoft.com/azure/api-management/api-management-key-concepts

Behind that answer, the agent made a model call that asked for a tool, one or more Learn tool calls, and a model call that wrote the answer, all through the gateway. Stop the agent with Ctrl+C.

Checkpoint

The local agent answers with a Microsoft Learn URL.

#Deploy to Foundry

1

#Provision and deploy

Bash
azd up

azd asks for a subscription if the environment doesn't have one. Then it creates rg-aigw-lab16 with a Foundry resource and a project that has hosted agents enabled, uploads src/gateway-agent as a code package, and creates the hosted agent. Foundry builds it from requirements.txt. It takes about five minutes, and ends with:

Text
SUCCESS: Your application was deployed to Azure in 2 minutes 31 seconds.
2

#Invoke the hosted agent

Bash
azd ai agent invoke gateway-agent "Which Learn page explains Azure API Management key concepts? One sentence and the URL."

Expected output: the same kind of answer, now from Foundry. The first call can take 10 to 20 seconds while the agent starts.

Text
Agent:        gateway-agent (remote)
...
[gateway-agent] The Learn page titled "What is Azure API Management?" explains Azure API Management key concepts.
URL: https://learn.microsoft.com/azure/api-management/api-management-key-concepts

azd keeps the conversation, so a second invoke, such as "Shorten that to ten words.", continues it. Add --new-conversation to start over.

3

#Find the agent in Foundry

Bash
azd ai agent show gateway-agent

The output shows Status active, the agent's own identity, its Responses endpoint, and a Playground URL. Open that URL to chat with the agent in the Foundry portal.

Checkpoint

azd ai agent show gateway-agent reports active, and azd ai agent invoke returns an answer with a Learn URL.

#See the agent in Monitoring

The hosted-agent key is a caller identity of its own. With monitoring set up as in Monitor usage, cost, and traces, invoke the agent a few times, wait a few minutes, then open Monitoring in the portal:

  • Models: use the All caller identities filter to select hosted-agent. You see the agent's calls, tokens, and estimated cost for your alias.
  • Tools: the learn tool server under Usage by tool server, with the tools the agent called under Top tools within tool servers.
  • Traces: one row per model or tool call, with the policies the gateway applied.

#Cap the agent's tokens

Give the agent's alias a strict token limit counted per caller identity, then watch the gateway enforce it without any change to the agent. Pick one track.

Choose your track
1

#Add the token limit

  1. Select Policies›Add policy.
  2. On Type, select Token rate limit.
  3. On Scope, select Individual assets and pick your alias.
  4. On Configure, set Time period to Per minute, Allowed tokens to 1000, and Counter dimensions to Caller identity, then select Create.
1

#Add the token limit

Find the alias by the name that apps send, which works even when a portal-created alias contains /. az aigateway model-alias update --policies replaces the alias's whole policy array, so these commands keep its other policies:

ALIAS_NAME="$(az aigateway model-alias list -g "$RG" --gateway-name "$GATEWAY" \
  --query "[?properties.aliasName=='$AI_GATEWAY_MODEL'].name | [0]" -o tsv)"
az aigateway model-alias show -g "$RG" --gateway-name "$GATEWAY" -n "$ALIAS_NAME" -o json \
  | jq -c '[(.properties.policies // [])[] | select(.type != "tokenLimit") | del(.scope)] + [{type:"tokenLimit",period:"minute",count:1000,counterKey:["identity"]}]' > policies.json
az aigateway model-alias update -g "$RG" --gateway-name "$GATEWAY" -n "$ALIAS_NAME" --policies @policies.json \
  --query properties.policies
$ALIAS_NAME = az aigateway model-alias list -g $RG --gateway-name $GATEWAY `
  --query "[?properties.aliasName=='$($env:AI_GATEWAY_MODEL)'].name | [0]" -o tsv
$alias = az aigateway model-alias show -g $RG --gateway-name $GATEWAY -n $ALIAS_NAME -o json | ConvertFrom-Json
$p = @($alias.properties.policies | Where-Object { $_ -and $_.type -ne 'tokenLimit' } |
  Select-Object * -ExcludeProperty scope) +
  @(@{ type = 'tokenLimit'; period = 'minute'; count = 1000; counterKey = @('identity') })
ConvertTo-Json -InputObject $p -Depth 10 -Compress | Set-Content policies.json
az aigateway model-alias update -g $RG --gateway-name $GATEWAY -n $ALIAS_NAME --policies "@policies.json" `
  --query properties.policies
1

#Trigger the limit

Wait about 30 seconds for the policy to apply, then invoke the hosted agent twice:

Bash
azd ai agent invoke gateway-agent --new-conversation "Summarize Azure API Management in three sentences with Learn links."
azd ai agent invoke gateway-agent --new-conversation "Summarize Azure API Management in three sentences with Learn links."

The gateway counts tokens when a call completes, so the first invoke usually succeeds and uses well over 1,000 tokens, because Learn tool results are long. The second invoke fails, and the agent reports the gateway's 429:

Text
ERROR: agent failed (server_error): (... Error code: 429 - {'statusCode': 429, 'message': 'Token limit is exceeded. Try again in <n> seconds.'} ...)

The counter belongs to the hosted-agent key. Your other apps, with their own keys, keep their full allowance on the same alias. For more on limits, see Throttle tokens per caller with token limits.

2

#Remove the limit

In the portal, select Policies, open the Token rate limit you created for your alias, and delete it. With the CLI, remove the tokenLimit policy the same way you added it:

az aigateway model-alias show -g "$RG" --gateway-name "$GATEWAY" -n "$ALIAS_NAME" -o json \
  | jq -c '[(.properties.policies // [])[] | select(.type != "tokenLimit") | del(.scope)]' > policies.json
az aigateway model-alias update -g "$RG" --gateway-name "$GATEWAY" -n "$ALIAS_NAME" --policies @policies.json \
  --query properties.policies
rm policies.json
$alias = az aigateway model-alias show -g $RG --gateway-name $GATEWAY -n $ALIAS_NAME -o json | ConvertFrom-Json
$p = @($alias.properties.policies | Where-Object { $_ -and $_.type -ne 'tokenLimit' } |
  Select-Object * -ExcludeProperty scope)
ConvertTo-Json -InputObject $p -Depth 10 -Compress | Set-Content policies.json
az aigateway model-alias update -g $RG --gateway-name $GATEWAY -n $ALIAS_NAME --policies "@policies.json" `
  --query properties.policies
Remove-Item policies.json

If your alias had its own token limit before this lab, the CLI commands remove it too: add it back with the count it had. When the alias has no policies left, the update prints nothing.

#Verify

Verify
  • azd ai agent invoke --local and azd ai agent invoke both return an answer with a Microsoft Learn URL.
  • The Foundry project has no model deployments, yet the agent answers: its model calls go through the gateway.
  • With the token limit in place, the agent got 429 from the gateway without any code change.
  • With monitoring set up, Monitoring›Models shows calls from the hosted-agent caller identity.

#Go further

  • Go keyless. The hosted agent has its own Microsoft Entra identity, shown by azd ai agent show gateway-agent. Give it the AI Gateway User role, which covers models and MCP tools, as in Go keyless with Microsoft Entra ID and RBAC. Then send a Microsoft Entra token from DefaultAzureCredential to both endpoints instead of the key.
  • Keep the key out of the agent definition. Store it in Azure Key Vault and read it at startup with the agent's identity, instead of passing it as an environment variable.
  • Lock down egress. Foundry can restrict where a hosted agent may connect. Allow only your gateway's host name, so the gateway is the agent's only way out. See the egress control sample↗.
  • Use another framework. Swap the agent's internals for the OpenAI Agents SDK or LangGraph, as in Connect agent frameworks to models and tools. The gateway settings stay the same.
  • Charge the agent back. Attribute its tokens and estimated cost with Attribute tokens and cost with OpenTelemetry.

#Clean up

Delete the Foundry resource group and the hosted agent. --purge also purges the soft-deleted Foundry resource so you can reuse its name:

Bash
azd down --purge

Then delete the hosted-agent key: in Access›Keys, select … (More actions) on its row and delete it, or run az aigateway api-key delete -g "$RG" --gateway-name "$GATEWAY" -n hosted-agent --yes. Delete the .azure folder in infra if you no longer need the environment, because it holds the key value.

Your gateway, its alias, and the learn MCP server aren't affected.

#Troubleshooting

SymptomLikely causeFix
400 "Specify either an API key or an Authorization header, not both"The code sends the key as the SDK's API key and also in an api-key headerPass the key only as the SDK's api_key, and remove the api-key default header from the model client.
401 from the MCP endpointThe key went in Authorization: BearerThe MCP endpoint takes keys only in the api-key header, as in main.py.
401 from the model endpointThe key is wrong, suspended, or deletedCheck hosted-agent in Access›Keys, load the value again, run azd env set AI_GATEWAY_API_KEY, then azd deploy.
404 from the model endpointAI_GATEWAY_MODEL doesn't match an aliasCopy the alias exactly from the model's Aliases tab, run azd env set AI_GATEWAY_MODEL, then azd deploy.
429 "Token limit is exceeded"A token limit on the alias, such as the one from this labWait for the time in the message, or remove the policy.
429 from tool callsA request rate limit on the learn server, for example from Control which tools agents can callWait for the Retry-After time, or remove the policy from the MCP server.
RuntimeError: Set AI_GATEWAY_URLAn azd environment value is missingRun azd env set for the missing value, then azd ai agent run or azd deploy.
The hosted agent still uses an old valueFoundry reads environment variables when the agent version is createdRun azd deploy after every azd env set.
[CodeError] [tool.poetry] section not found during deploymentA pyproject.toml without a lock file was added to src/gateway-agentKeep requirements.txt as the dependency file, or commit a uv.lock next to pyproject.toml.
azd ai agent run can't download packages, with a certificate errorA proxy on your network inspects TLS trafficSet UV_SYSTEM_CERTS=true (UV_NATIVE_TLS=true in older uv versions) so uv trusts your system certificates, then run it again.
