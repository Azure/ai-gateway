Governance & cost · Lab 09

Set gateway-wide policy baselines

Apply a baseline of token limit, request rate limit, content safety, and IP filter policies at Gateway scope so every model and MCP server, including the ones you add later, starts with the same guardrails, then layer stricter asset policies on top.

Intermediate 25 min PortalRESTBicep Updated Oct 14, 2026
Source Edit

What you'll do

  • Explain how Gateway scope policies and asset policies layer, and why any applicable policy can block a call
  • Apply a token limit, request rate limit, content safety, and IP filter baseline at Gateway scope
  • Keep the baseline in a reviewed policy file and apply it with a merge-safe script
  • Verify the baseline from your own IP address and see a stricter model policy take effect on top of it

Before you start

  • 06Throttle tokens per caller with token limits
  • 08Screen prompts and responses with content safety

Tracks: Portal, REST, Bicep / azd

Your gateway now serves several models and MCP servers, and teams add new ones every week. Some assets have carefully tuned policies, and some have none at all. The platform and security teams agree on a baseline that every asset gets by default: a generous token limit, a request rate limit, Balanced content safety, and runtime access only from approved networks. In this lab you apply that baseline once, at Gateway scope, and keep tighter asset policies on top of it.

#Before you begin

  • Complete Throttle tokens per caller with token limits and Screen prompts and responses with content safety, including their Clean up sections. You need a gateway, an imported model, a callable alias, and a runtime API key from Access›Keys.
  • For the REST and Policy as code tracks: the Azure CLI↗ 2.75 or later, signed in with az login, plus jq (Bash) or PowerShell 7 or later. There's no az aigateway command for Gateway scope policies, so these tracks call the management API with az rest.
  • For Verify: curl and jq (Bash) or PowerShell 7 or later, and the aigateway CLI extension (install it↗).
  • Permission to change the gateway, for example Contributor on the resource group.
  • The public IP addresses or CIDR ranges your callers use. Once the IP filter is on, calls from anywhere else get 403.

Set these variables once. Every track and the Verify section reuse them.

export RG="<resource-group>"
export GATEWAY="<gateway>"
export PROVIDER="<provider-name>"          # for example foundry-models
export MODEL="<model-name>"                # the backend model name under that provider

export AI_GATEWAY_URL="$(az aigateway show -g "$RG" -n "$GATEWAY" --query properties.gatewayUrl -o tsv)"
# For Foundry imports, the default alias matches the deployment's model name.
export AI_GATEWAY_MODEL="$(az aigateway model show -g "$RG" --gateway-name "$GATEWAY" \
  --provider-name "$PROVIDER" -n "$MODEL" --query properties.deployment.modelName -o tsv)"
# Paste the runtime key you created in Access › Keys. Don't commit it or write it to a file.
read -rsp "AI Gateway API key: " AI_GATEWAY_API_KEY && export AI_GATEWAY_API_KEY && echo

export MY_IP="$(curl -s https://api.ipify.org)" && echo "$MY_IP"

#How it works

A policy with Gateway scope is stored on the gateway's default workspace instead of on one asset. It applies to every compatible model, alias, and MCP server, including assets you add later, without another policy update. Asset policies keep working alongside it. The gateway evaluates every applicable policy before it forwards a request, and if any one of them blocks, the client gets an error and the backend is never called. So an asset policy can make the rules tighter for one asset, but it can't loosen the baseline.

This lab's baseline:

PolicyApplies toBaseline valueBlocked calls get
Token rate limitModels100,000 tokens per minute, per caller identity429 with Retry-After
Request rate limitModels and MCP servers600 calls per 60 seconds, per caller identity429 with Retry-After
Content safetyModels and MCP serversBalanced (Medium) for all four categories400
IP filterModels and MCP serversAllow listed IPs only: your CIDR ranges403

A Gateway scope Cost limit is one budget across all models; you can add it in Enforce cost budgets with per-caller overrides. Agent 365 tool threat protection can't be set at Gateway scope; it applies to individual MCP servers.

Warning

The IP filter applies to runtime calls. You keep managing the gateway in the portal and with az rest, so you can always fix the list. But every caller outside it gets 403: teammates, CI pipelines, hosted agents, and your own machine when you switch networks or VPN. Remove it in Clean up.

#Read the Gateway scope policies

Gateway scope policies live inline in the properties.policies array of the gateway's default workspace. A PATCH replaces the whole array, so always read it first and keep the policies you didn't mean to change.

SUB="$(az account show --query id -o tsv)"
URL="https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$GATEWAY/workspaces/default?api-version=2025-09-01-preview"

az rest --method get --url "$URL" --query properties.policies
$SUB = az account show --query id -o tsv
$URL = "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$GATEWAY/workspaces/default`?api-version=2025-09-01-preview"

az rest --method get --url $URL --query properties.policies
2

#Merge the baseline and keep everything else

The baseline replaces any existing policy of the same four types and keeps every other entry, such as a Gateway scope cost limit.

BASELINE="$(jq -cn --arg cidrs "$ALLOWED_CIDRS" '[
  {"type":"tokenLimit","count":100000,"period":"minute","counterKey":"Identity","scope":"workspace"},
  {"type":"requestRateLimit","callsPerPeriod":600,"periodSeconds":60,"counterKey":"Identity","scope":"workspace"},
  {"type":"contentSafety","hateSeverity":"Medium","violenceSeverity":"Medium","sexualSeverity":"Medium","selfHarmSeverity":"Medium"},
  {"type":"ipFilter","action":"Allow","cidrRanges":($cidrs | split(",") | map(gsub("\\s"; "")) | map(select(length > 0)))}
]')"
jq '.[] | select(.type == "ipFilter")' <<<"$BASELINE"    # check the allowed ranges before you apply

POLICIES="$(az rest --method get --url "$URL" | jq -c --argjson baseline "$BASELINE" '
  [(.properties.policies // [])[] | select(.type | IN($baseline[].type) | not)] + $baseline')"

az rest --method patch --url "$URL" --body "{\"properties\":{\"policies\":$POLICIES}}"
$baseline = @(
  [pscustomobject]@{ type = 'tokenLimit'; count = 100000; period = 'minute'; counterKey = 'Identity'; scope = 'workspace' }
  [pscustomobject]@{ type = 'requestRateLimit'; callsPerPeriod = 600; periodSeconds = 60; counterKey = 'Identity'; scope = 'workspace' }
  [pscustomobject]@{ type = 'contentSafety'; hateSeverity = 'Medium'; violenceSeverity = 'Medium'; sexualSeverity = 'Medium'; selfHarmSeverity = 'Medium' }
  [pscustomobject]@{ type = 'ipFilter'; action = 'Allow'; cidrRanges = @($env:ALLOWED_CIDRS -split ',' | ForEach-Object { $_.Trim() } | Where-Object { $_ }) }
)
$baseline | Where-Object type -eq 'ipFilter' | ConvertTo-Json    # check the allowed ranges before you apply

$current  = az rest --method get --url $URL | ConvertFrom-Json
$policies = @($current.properties.policies | Where-Object { $_ -and $_.type -notin $baseline.type })
$policies += $baseline

$body = @{ properties = @{ policies = $policies } } | ConvertTo-Json -Depth 10 -Compress
$body | Set-Content -Path patch.json
az rest --method patch --url $URL --body '@patch.json'
Remove-Item patch.json
Note

When you create a token or request rate limit at Gateway scope, the portal writes "scope": "workspace" into the policy object. The REST and Policy as code tracks include the same field so that every track creates the same policy. If the API rejects a field, create the policy once in the portal, then copy its shape from the GET response.

Checkpoint

Running the GET again returns your other policies unchanged plus tokenLimit, requestRateLimit, contentSafety, and ipFilter entries, with your ranges in cidrRanges.

1

#Choose what to declare

Gateway scope policies live on the gateway's default workspace. The sample Bicep templates only reference that workspace as existing. Declaring it in your own template would send a PUT that replaces the whole workspace resource, including settings that the template doesn't list. Instead, keep the baseline in a policy file that goes through code review, and apply it with a script that does the same GET, merge, and PATCH as the REST track.

infra/apply-baseline.shGitHub
#!/usr/bin/env bash
# Applies the policy baseline in baseline-policies.json at Gateway scope (the gateway's default
# workspace). It reads the current Gateway scope policies, replaces the entries whose type is in
# the baseline, keeps every other policy, and patches the workspace.
#
# Usage:
#   export RG="<resource-group>" GATEWAY="<gateway>"
#   export ALLOWED_CIDRS="198.51.100.7/32"   # comma-separated CIDR ranges for the IP filter
#   ./apply-baseline.sh              # apply the baseline
#   ./apply-baseline.sh --dry-run    # print the merged policies without changing anything
#   ./apply-baseline.sh --remove     # remove the baseline policy types from Gateway scope
#
# Set BASELINE_FILE to use a different policy file. Requires the Azure CLI (az login) and jq.
set -euo pipefail

MODE="apply"
case "${1:-}" in
  "") ;;
  --dry-run) MODE="dry-run" ;;
  --remove) MODE="remove" ;;
  *) echo "Unknown option: $1. Use --dry-run or --remove." >&2; exit 2 ;;
esac

: "${RG:?Set RG to your resource group}"
: "${GATEWAY:?Set GATEWAY to your gateway name}"

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
BASELINE_FILE="${BASELINE_FILE:-$SCRIPT_DIR/baseline-policies.json}"
BASELINE="$(jq -c '.' "$BASELINE_FILE")"

# The file holds a placeholder address for the IP filter. Never apply it: replace it with ALLOWED_CIDRS.
if [ "$MODE" != "remove" ] && jq -e 'any(.[]; .type == "ipFilter")' >/dev/null <<<"$BASELINE"; then
  : "${ALLOWED_CIDRS:?Set ALLOWED_CIDRS to the comma-separated CIDR ranges to allow, for example \"\$(curl -s https://api.ipify.org)/32\"}"
  BASELINE="$(jq -c --arg cidrs "$ALLOWED_CIDRS" '
    map(if .type == "ipFilter"
        then .cidrRanges = ($cidrs | split(",") | map(gsub("\\s"; "")) | map(select(length > 0)))
        else . end)' <<<"$BASELINE")"
  if ! jq -e 'all(.[] | select(.type == "ipFilter"); (.cidrRanges | length) > 0)' >/dev/null <<<"$BASELINE"; then
    echo "ALLOWED_CIDRS doesn't contain any CIDR ranges." >&2
    exit 2
  fi
  INVALID="$(jq -r '[.[] | select(.type == "ipFilter") | .cidrRanges[] | select(contains("/") | not)] | join(", ")' <<<"$BASELINE")"
  if [ -n "$INVALID" ]; then
    echo "Use CIDR notation with a prefix length, for example $INVALID/32 for a single address." >&2
    exit 2
  fi
fi

SUB="$(az account show --query id -o tsv)"
URL="https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.ApiManagement/service/$GATEWAY/workspaces/default?api-version=2025-09-01-preview"

# A PATCH replaces the whole properties.policies array, so always merge with the current array.
CURRENT="$(az rest --method get --url "$URL")"
KEEP='[(.properties.policies // [])[] | select(.type | IN($baseline[].type) | not)]'
if [ "$MODE" = "remove" ]; then
  POLICIES="$(jq -c --argjson baseline "$BASELINE" "$KEEP" <<<"$CURRENT")"
else
  POLICIES="$(jq -c --argjson baseline "$BASELINE" "$KEEP + \$baseline" <<<"$CURRENT")"
fi

if [ "$MODE" = "dry-run" ]; then
  echo "Gateway scope policies after the change (nothing was applied):"
  jq '.' <<<"$POLICIES"
  exit 0
fi

if [ "$MODE" = "apply" ] && jq -e 'any(.[]; .type == "ipFilter")' >/dev/null <<<"$BASELINE"; then
  echo "The IP filter allows runtime calls only from: $(jq -r '[.[] | select(.type == "ipFilter") | .cidrRanges[]] | join(", ")' <<<"$BASELINE")"
fi

az rest --method patch --url "$URL" --body "{\"properties\":{\"policies\":$POLICIES}}" --output none

echo "Gateway scope policies on $GATEWAY:"
az rest --method get --url "$URL" | jq -r '
  (.properties.policies // []) as $p
  | if ($p | length) == 0 then "  (none)" else $p[] | "  \(.type)  \(del(.type) | tojson)" end'

On GitHub, open infra/apply-baseline.sh↗ or infra/apply-baseline.ps1↗.

Tip

3

#Layer a stricter model policy

Add a deliberately low token limit to your model only, the same one you used in lab 06:

Bash
az aigateway model policy set-token-limit \
  -g "$RG" --gateway-name "$GATEWAY" --provider-name "$PROVIDER" -n "$MODEL" \
  --token-limit 1000 --token-period minute --token-counter-key Identity

Then send a burst with the script from lab 06:

../06-token-limits/infra/trigger-token-limit.sh "$AI_GATEWAY_MODEL" 8
../06-token-limits/infra/trigger-token-limit.ps1 -Model $env:AI_GATEWAY_MODEL -Requests 8

After three or four requests, the gateway returns 429. The baseline allows 100,000 tokens per minute, but the model's tighter limit is evaluated too, and it blocks. Remove the model limit and run the burst again:

Bash
az aigateway model policy remove \
  -g "$RG" --gateway-name "$GATEWAY" --provider-name "$PROVIDER" -n "$MODEL" \
  --remove-token-limit true

All eight requests now return 200, because only the generous baseline applies.

4

#See the IP filter block a call (optional)

Point the allow list at a documentation address that can't be yours, call the model, then restore your range.

  • Portal: in Policies, select Edit on the IP filter policy, set the ranges to 203.0.113.10/32, and save.
  • Script (Bash): ALLOWED_CIDRS="203.0.113.10/32" ./infra/apply-baseline.sh
  • Script (PowerShell): ./infra/apply-baseline.ps1 -ResourceGroup $RG -Gateway $GATEWAY -AllowedCidrs "203.0.113.10/32"

Run check-call again. It now returns Status: 403, and the request never reaches the model. Restore your range in the portal, or run the script again without the override (./infra/apply-baseline.sh, or the PowerShell script without -AllowedCidrs), and check that check-call returns 200. If you still see the old result, wait a minute and retry.

5

#Watch outcomes in Monitoring

If you configured Application Insights in Monitor usage, cost, and traces, open Monitoring and compare 400, 403, and 429 outcomes before and after the baseline. A sudden rise in 403 usually means a caller's network isn't on the allow list.

Checkpoint

Policies shows four Gateway scope policies. Your own call returned 200, a stricter model limit still returned 429 on top of the baseline, and you know how a blocked IP address looks (403).

#Go further

  • Cap spend gateway-wide. Add a Cost limit with Gateway scope for one budget across all models, as described in Enforce cost budgets with per-caller overrides.

#Clean up

Remove the baseline before you continue, especially the IP filter: later labs call the gateway from hosted agents and other networks, which would get 403. In your own environment, you can keep the other three policies and replace the IP filter with your organization's egress ranges.

#Troubleshooting

SymptomLikely causeFix
Every call returns 403Your public IP address changed (new network, VPN, or hotspot), or your network reaches the gateway from a different address than the one api.ipify.org reportedCheck curl -s https://api.ipify.org again and update the IP filter. If you use a proxy or split-tunnel VPN, ask your network team for the egress ranges. Management calls still work, so you can always fix the list.
Teammates, pipelines, or hosted agents get 403Their egress addresses aren't on the allow listAdd their CIDR ranges, or remove the IP filter until you know them.
