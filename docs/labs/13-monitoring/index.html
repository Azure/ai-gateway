Observability & FinOps · Lab 13

Monitor usage, cost, and traces

Send the gateway's OpenTelemetry metrics, logs, and traces to Application Insights, then use the built-in Monitoring dashboard to see usage, estimated cost per model and API key, policy impact, and gateway-aware traces.

Beginner 25 min PortalBicep Updated Oct 28, 2026
Source Edit

What you'll do

  • Explain how the gateway exports metrics, logs, and traces independently over OTLP
  • Connect the gateway to Application Insights in the portal, or with Bicep and azd
  • Read health, outcomes, policy impact, tokens, and estimated cost on the Monitoring dashboard
  • Follow one request through the trace waterfall, including its policy child spans
  • Query gateway telemetry in Log Analytics with KQL

Before you start

  • 02Publish a Foundry model and make your first call

Tracks: Portal, Bicep + azd

Your gateway now serves several apps. Finance asks what the models cost per team, an app owner reports intermittent failures, and nobody can tell whether a policy or the backend rejected those calls. In this lab you send the gateway's OpenTelemetry signals to Application Insights and answer all three questions from the built-in Monitoring dashboard, down to a single request's trace.

#How it works

The gateway emits three OpenTelemetry signals and exports each one independently over OTLP, to Azure Application Insights or to any OTLP endpoint (for example Datadog, Splunk, Grafana Cloud, or your own collector). Configure only the signals you need. Telemetry follows the OpenTelemetry GenAI and MCP semantic conventions, such as gen_ai.request.model, gen_ai.operation.name, and mcp.method.name, and adds gateway attributes such as the API key, alias, resolved model, and policy type.

When the destination is Application Insights and all three signals are on, the Monitoring page turns that data into a dashboard. Estimated cost is observed tokens × public pricing: use it to spot trends and compare callers, then reconcile with provider billing or Azure Cost Management for financial reporting.

SignalWhat the gateway sendsWhere it lands with Application InsightsDashboard uses it for
MetricsToken usage and estimated token cost, by model, token type, API key, and callerAzure Monitor workspace (managed Prometheus) linked to Application InsightsTokens and Estimated model cost
TracesOne root span per request, with child spans for each stage and each policy that ranOTelSpans table in the Log Analytics workspaceCalls, outcomes, blocked traces, the trace waterfall
LogsRequest records with status, caller, model, and the token usage the backend reportedOTelLogs table in the Log Analytics workspaceCorrelated logs and caller attribution

#Connect Application Insights

Pick one track. Both end with the gateway exporting all three signals to an Application Insights resource named <gateway>-insights.

Choose your track
1

#Start the setup

Open the AI Gateway portal↗ and select your gateway from the gateway switcher. Select Monitoring. If monitoring isn't configured yet, the page shows Set up monitoring. Select Configure telemetry. The wizard has three steps: Destination, Authentication, and Review and apply.

2

#Choose a destination

On Destination, select New Azure Application Insights resource and keep the suggested name, <gateway>-insights. Select Next.

Tip

The other choices are Existing Azure Application Insights resource, for a component you already have, and Custom OpenTelemetry destination, which takes separate Metrics endpoint, Logs endpoint, and Traces endpoint URLs. Leave an endpoint empty to turn that signal off. The built-in dashboard only reads Application Insights, so with a custom destination you use your own platform's views.

3

#Review authentication

On Authentication, the gateway exports with its managed identity. If none is enabled, the wizard enables the system-assigned identity for you. It also assigns the Monitoring Metrics Publisher role on the destination's Data Collection Rule when you apply.

Leave Include recommended token claims in telemetry selected. It adds Microsoft Entra caller claims to the telemetry, which Attribute tokens and cost with OpenTelemetry builds on. Select Next.

4

#Apply the configuration

On Review and apply, select Apply. The wizard shows each step as it runs: Register resource providers, Resolve managed identity, Provision destination, Discover OTLP endpoints, Assign Monitoring Metrics Publisher role, and Create telemetry exporter. If a step fails, fix the cause shown in the message and select Retry. If an Azure Policy assignment blocks a step, check the Activity Log for the denied operation.

Checkpoint

The Monitoring page shows the Overview, Models, Tools, Policies, and Traces tabs, with Open in Azure portal and Settings in the header.

What you need: only the one-time setup from Before you begin. This track doesn't use your gateway from lab 02: azd up creates a new one, so it works on its own.

1

#Choose what to declare

The templates declare what the portal's wizard sets up: a Log Analytics workspace, a workspace-based Application Insights component with OTLP ingestion turned on, and a gateway telemetry exporter of kind OpenTelemetry that sends metrics, logs, and traces to the component's OTLP endpoints with the recommended token claims. When OTLP ingestion turns on, Azure creates a managed resource group, ai_<component>_<id>_managed, with the Data Collection Rule and the Azure Monitor workspace for the metrics. The template reads the endpoints back from the component.

The gateway's managed identity also needs Monitoring Metrics Publisher on that Data Collection Rule. Azure locks the managed resource group with a deny assignment that blocks deployments, so Bicep can't assign the role there. Instead, azure.yaml assigns it with the Azure CLI in a postprovision hook, which azd runs after each deployment.

The sample's exporter kind, applicationInsights, is legacy: the portal flags it because it no longer activates the OTLP signals the dashboard needs. infra/monitoring.bicep keeps it for reference, switched off by deployLegacyExporter.

2

#Review the templates

  name: 'rg-${environmentName}'

  tags: tags

infra/monitoring.bicep creates the Log Analytics workspace and the Application Insights component, and turns on OTLP ingestion when enableOtlpIngestion is true. You can also deploy it on its own to your gateway's resource group with az deployment group create, then connect it in the portal with Existing Azure Application Insights resource:

infra/monitoring.bicepGitHub
// Creates the Application Insights destination for AI Gateway telemetry: a Log Analytics workspace and a
// workspace-based Application Insights component.
//
// The lab's main.bicep calls it with azd, sets enableOtlpIngestion, and then connects the gateway with
// otel-exporter.bicep. You can also deploy it on its own to the resource group of an existing gateway, then connect
// the gateway in the portal: Monitoring › Configure telemetry › Existing Azure Application Insights resource. The
// portal enables OTLP ingestion on the component, grants the gateway's managed identity the Monitoring Metrics
// Publisher role, and creates an OpenTelemetry exporter.

@description('Name of the existing AI Gateway (Microsoft.ApiManagement/aigateways).')
param gatewayName string

@description('Location for the monitoring resources.')
param location string = resourceGroup().location

@description('Application Insights component name. The portal suggests <gateway>-insights for new destinations.')
param appInsightsName string = '${gatewayName}-insights'

@description('Log Analytics workspace that stores the OTelSpans and OTelLogs tables.')
param logAnalyticsWorkspaceName string = take('${gatewayName}-logs', 63)

@description('Tags applied to the monitoring resources.')
param tags object = {}

@description('Also create the sample\'s telemetry exporter (kind applicationInsights). The portal flags this kind as legacy because it no longer activates OTLP signals. Leave false and connect in the portal.')
param deployLegacyExporter bool = false

@description('Turn on OTLP ingestion on the component, as the portal does when you connect it. Azure then creates a managed Azure Monitor workspace, data collection endpoint, and data collection rule, and the component reports its OTLP endpoints.')
param enableOtlpIngestion bool = false

resource logAnalyticsWorkspace 'Microsoft.OperationalInsights/workspaces@2023-09-01' = {
  name: logAnalyticsWorkspaceName
  location: location
  tags: tags
  properties: {
    retentionInDays: 30
    features: {
      enableLogAccessUsingOnlyResourcePermissions: true
    }
    sku: {
      name: 'PerGB2018'
    }
  }
}

resource appInsights 'Microsoft.Insights/components@2020-02-02' = {
  name: appInsightsName
  location: location
  kind: 'web'
  tags: tags
  // AzureMonitorWorkspaceIngestionMode isn't in the Bicep types for this API version yet, so union() adds it.
  properties: union(
    {
      Application_Type: 'web'
      WorkspaceResourceId: logAnalyticsWorkspace.id
    },
    enableOtlpIngestion ? { AzureMonitorWorkspaceIngestionMode: 'Enabled' } : {}
  )
}

// Read-only properties that the component reports once OTLP ingestion is on. any() skips the missing Bicep types.
var otlp = any(appInsights.properties)

#disable-next-line BCP081
resource gateway 'Microsoft.ApiManagement/aigateways@2025-09-01-preview' existing = {
  name: gatewayName
}

#disable-next-line BCP081
resource defaultWorkspace 'Microsoft.ApiManagement/aigateways/workspaces@2025-09-01-preview' existing = {
  parent: gateway
  name: 'default'
}

// The reference sample's exporter, unchanged. Kept for reference only: see deployLegacyExporter.
#disable-next-line BCP081
resource telemetryExporter 'Microsoft.ApiManagement/aigateways/workspaces/telemetryExporters@2025-09-01-preview' = if (deployLegacyExporter) {
  parent: defaultWorkspace
  name: 'appinsights'
  properties: {
    kind: 'applicationInsights'
    payloadCapture: false
    applicationInsights: {
      connectionString: appInsights.properties.ConnectionString
      resourceId: appInsights.id
    }
  }
}

output appInsightsId string = appInsights.id
output appInsightsName string = appInsights.name
output logAnalyticsWorkspaceId string = logAnalyticsWorkspace.id
output logAnalyticsWorkspaceName string = logAnalyticsWorkspace.name
output logAnalyticsCustomerId string = logAnalyticsWorkspace.properties.customerId
output dataCollectionRuleId string = otlp.?DataCollectionRuleResourceId ?? ''
output otlpMetricsEndpoint string = otlp.?OTLPMetricsEndpoint ?? ''
output otlpLogsEndpoint string = otlp.?OTLPLogsEndpoint ?? ''
output otlpTracesEndpoint string = otlp.?OTLPTracesEndpoint ?? ''

infra/otel-exporter.bicep creates the exporter. The claimAttributes parameter lists the token claims to add to the telemetry, and the signals that carry each one. Its default matches Include recommended token claims in telemetry:

infra/otel-exporter.bicepGitHub
// Connects an AI Gateway to Application Insights over OpenTelemetry, the same way the portal's Configure telemetry
// wizard does: an OpenTelemetry exporter that sends metrics, logs, and traces to the component's OTLP endpoints, with
// the token claims to add to the telemetry.
// Turn on OTLP ingestion on the component first (monitoring.bicep with enableOtlpIngestion=true): it creates the
// data collection rule and the endpoints. The gateway's system-assigned identity also needs Monitoring Metrics
// Publisher on that rule. Azure keeps the rule in a managed resource group whose deny assignment blocks deployments,
// so Bicep can't assign it: the lab's azure.yaml does it with the Azure CLI after "azd provision", using the
// gatewayPrincipalId and dataCollectionRuleId outputs. The lab's main.bicep calls this file with azd. You can also
// deploy it on its own to the resource group of an existing gateway and component, then assign the role yourself.
targetScope = 'resourceGroup'

@description('Name of the existing AI Gateway (Microsoft.ApiManagement/aigateways) in this resource group.')
param gatewayName string

@description('Name of the existing Application Insights component in this resource group, with OTLP ingestion on.')
param appInsightsName string

@description('Name of the telemetry exporter. The portal names it appinsights.')
param exporterName string = 'appinsights'

@description('Token claims to add to the telemetry, and the signals that carry each one. The default is the portal\'s "Include recommended token claims in telemetry".')
param claimAttributes array = [
  {
    source: { kind: 'claims', value: 'tid' }
    signals: ['logs', 'traces', 'metrics']
  }
  {
    source: { kind: 'claims', value: 'oid' }
    signals: ['logs', 'traces', 'metrics']
  }
  {
    source: { kind: 'claims', value: 'appid' }
    signals: ['logs', 'traces']
  }
  {
    source: { kind: 'claims', value: 'azp' }
    signals: ['logs', 'traces']
  }
]

@description('Log request and response payloads. Off by default: prompts and responses can be sensitive and add volume.')
param payloadCapture bool = false

#disable-next-line BCP081
resource gateway 'Microsoft.ApiManagement/aigateways@2025-09-01-preview' existing = {
  name: gatewayName
}

#disable-next-line BCP081
resource defaultWorkspace 'Microsoft.ApiManagement/aigateways/workspaces@2025-09-01-preview' existing = {
  parent: gateway
  name: 'default'
}

resource appInsights 'Microsoft.Insights/components@2020-02-02' existing = {
  name: appInsightsName
}

// The OTLP properties aren't in the Bicep types for this API version yet. any() skips the type check.
var otlp = any(appInsights.properties)

#disable-next-line BCP081
resource telemetryExporter 'Microsoft.ApiManagement/aigateways/workspaces/telemetryExporters@2025-09-01-preview' = {
  parent: defaultWorkspace
  name: exporterName
  properties: {
    kind: 'OpenTelemetry'
    payloadCapture: payloadCapture
    applicationInsights: {
      resourceId: appInsights.id
    }
    openTelemetry: {
      metricsEndpoint: otlp.OTLPMetricsEndpoint
      logsEndpoint: otlp.OTLPLogsEndpoint
      tracesEndpoint: otlp.OTLPTracesEndpoint
      credentials: {
        managedIdentity: {
          resource: 'https://monitor.azure.com'
        }
      }
    }
    telemetry: {
      attributes: claimAttributes
    }
  }
}

output telemetryExporterId string = telemetryExporter.id
output telemetryExporterName string = telemetryExporter.name
@description('Grant this principal Monitoring Metrics Publisher on the data collection rule.')
output gatewayPrincipalId string = gateway.identity.principalId
output dataCollectionRuleId string = otlp.DataCollectionRuleResourceId

azure.yaml holds the postprovision hook that grants the role:

azure.yamlGitHub
# yaml-language-server: $schema=https://raw.githubusercontent.com/Azure/azure-dev/main/schemas/v1.0/azure.yaml.json
# Lab 13: "azd up" creates the quick start's gateway, model, and runtime API key, then an Application Insights
# destination, and connects the gateway to it over OpenTelemetry.
# The lab clones the repo's main branch from GitHub and runs azd up in this folder.
name: aigw-lab13
metadata:
  template: aigw-lab13@1.0.0
infra:
  provider: bicep
  path: infra
hooks:
  # Bicep can't deploy into the data collection rule's managed resource group, so azd grants the gateway's identity
  # Monitoring Metrics Publisher on the rule with the Azure CLI after every provision. Running it again is harmless.
  postprovision:
    posix:
      shell: sh
      run: >-
        az role assignment create --assignee-object-id "$AI_GATEWAY_PRINCIPAL_ID"
        --assignee-principal-type ServicePrincipal --role "Monitoring Metrics Publisher"
        --scope "$DATA_COLLECTION_RULE_ID" --output none
    windows:
      shell: pwsh
      run: >-
        az role assignment create --assignee-object-id $env:AI_GATEWAY_PRINCIPAL_ID
        --assignee-principal-type ServicePrincipal --role "Monitoring Metrics Publisher"
        --scope $env:DATA_COLLECTION_RULE_ID --output none

#Follow a request through the trace waterfall

A gateway-aware trace shows where time went and which policies ran, so you can tell a policy rejection from a backend failure at a glance.

1

#Open a successful trace

On Traces, select a successful model call. The header shows the Trace ID, the number of Spans, and the Duration.

2

#Read the waterfall

Trace waterfall draws parent-first spans on one timeline. The root span is the model request, for example Model · <model-name> on POST /default/models/*. Under it:

Child spanWhat it measures
inboundWork before the backend call. Each policy that ran is a child span, such as policy costLimit with its configuration.
backendThe call to the provider, for example HTTP POST on /openai/v1/chat/completions.
outboundWork on the response before it returns to the client.
response transferSending the response back to the client.
3

#Read the correlated logs

Under Correlated logs, expand the request log and switch between Code and Tree. Look for:

  • gen_ai.operation.name (for example chat), gen_ai.request.model (the alias you sent), and gen_ai.response.model (the versioned model that answered).
  • azure.ai_gateway.client.usage.prompt_tokens, ...completion_tokens, and ...total_tokens: the usage the backend reported for this one call.
Checkpoint

You can point to the policy spans under inbound, compare backend time with total time, and read the token usage of one request in its correlated log.

#Query telemetry with KQL

The dashboard reads the OTelSpans and OTelLogs tables in the Log Analytics workspace behind Application Insights. You can query them directly to build your own reports and alerts.

1

#Open Logs

In the Azure portal↗, open the Log Analytics workspace linked to your Application Insights resource (<gateway>-logs if you used the Bicep + azd track) and select Logs. Switch the editor to KQL mode.

2

#Run the starter queries

Copy a query from infra/queries.kql↗ and run it. Start with query 2 (calls by alias, resolved model, and API key) and query 3 (token usage per model and API key).

infra/queries.kqlGitHub
// Starting-point KQL queries for AI Gateway telemetry. Adapt them to your traffic before you rely on them.
//
// Where to run them: the Log Analytics workspace behind your Application Insights resource, Logs, KQL mode.
// Select one query and run it.
//
// AI Gateway exports OpenTelemetry (OTLP) signals. Traces land in the OTelSpans table and logs in the
// OTelLogs table; span and log attributes are in the dynamic Attributes column. Attribute names follow the
// OpenTelemetry GenAI and MCP semantic conventions (gen_ai.request.model, gen_ai.response.model,
// gen_ai.operation.name, gen_ai.tool.name, mcp.method.name) plus gateway attributes (azure.ai_gateway.*,
// azure.apim.*). Run `OTelSpans | take 10` first and check the names your data actually carries.
// Token and cost metrics go to the Azure Monitor workspace (Prometheus), not to these tables.

// 1. Model and tool server requests over time, by outcome
OTelSpans
| where TimeGenerated > ago(24h)
| where Kind =~ "Server"
| extend Route = tostring(Attributes["http.route"]),
         Status = coalesce(toint(Attributes["http.response.status_code"]), toint(Attributes["http.status_code"]), toint(ResultCode))
| extend Asset = case(Route contains "/models/", "model", Route contains "/toolservers/", "tool server", "other"),
         Outcome = case(Status between (200 .. 399), "2xx-3xx", Status between (400 .. 499), "4xx", Status >= 500, "5xx", "unknown")
| summarize Requests = count() by bin(TimeGenerated, 15m), Series = strcat(Asset, " ", Outcome)
| render timechart

// 2. Model calls by requested alias, resolved model, and API key, with errors and latency
OTelSpans
| where TimeGenerated > ago(24h)
| where Kind =~ "Server" and tostring(Attributes["http.route"]) contains "/models/"
| extend RequestedModel = tostring(Attributes["gen_ai.request.model"]),
         ResolvedModel = tostring(Attributes["azure.ai_gateway.resolved_model.name"]),
         ApiKeyId = tostring(Attributes["azure.ai_gateway.api_key_id"]),
         Status = coalesce(toint(Attributes["http.response.status_code"]), toint(Attributes["http.status_code"]), toint(ResultCode))
| summarize Calls = count(), Errors4xx = countif(Status between (400 .. 499)), Errors5xx = countif(Status >= 500),
            P95DurationMs = percentile(DurationMs, 95)
    by RequestedModel, ResolvedModel, ApiKeyId
| order by Calls desc

// 3. Token usage reported by the backend, per model and API key (from request logs)
//    Chat Completions reports prompt/completion tokens; the Responses API reports input/output tokens.
//    Cached input tokens are part of the input tokens. Missing usage means "unknown", not zero.
OTelLogs
| where TimeGenerated > ago(24h)
| extend Model = tostring(Attributes["gen_ai.request.model"]),
         ApiKeyId = tostring(Attributes["azure.ai_gateway.api_key_id"]),
         InputTokens = coalesce(tolong(Attributes["azure.ai_gateway.client.usage.prompt_tokens"]), tolong(Attributes["azure.ai_gateway.client.usage.input_tokens"])),
         OutputTokens = coalesce(tolong(Attributes["azure.ai_gateway.client.usage.completion_tokens"]), tolong(Attributes["azure.ai_gateway.client.usage.output_tokens"])),
         CachedInputTokens = coalesce(tolong(Attributes["azure.ai_gateway.client.usage.prompt_tokens_details.cached_tokens"]), tolong(Attributes["azure.ai_gateway.client.usage.input_tokens_details.cached_tokens"]))
| where isnotnull(InputTokens) or isnotnull(OutputTokens)
| summarize Requests = count(), InputTokens = sum(InputTokens), CachedInputTokens = sum(CachedInputTokens),
            OutputTokens = sum(OutputTokens)
    by Model, ApiKeyId
| extend TotalTokens = InputTokens + OutputTokens
| order by TotalTokens desc

// 4. Policy impact: which policies ran, and how often the request ended in 4xx
//    A 4xx on a trace where a policy ran usually means that policy rejected it. Open the trace to confirm.
let requests = OTelSpans
| where TimeGenerated > ago(24h)
| where Kind =~ "Server"
| project TraceId, Status = coalesce(toint(Attributes["http.response.status_code"]), toint(Attributes["http.status_code"]), toint(ResultCode));
OTelSpans
| where TimeGenerated > ago(24h)
| extend PolicyType = tostring(Attributes["azure.apim.policy.type"]), ErrorType = tostring(Attributes["error.type"])
| where isnotempty(PolicyType)
| where PolicyType !in ("forward-request", "set-backend-service", "llm-emit-token-metric", "llm-emit-cost-metric")
| join kind=inner requests on TraceId
| summarize Requests = dcount(TraceId), RequestsEndingIn4xx = dcountif(TraceId, Status between (400 .. 499)),
            ErrorTypes = make_set_if(ErrorType, isnotempty(ErrorType), 5), LastExecuted = max(TimeGenerated)
    by PolicyType
| order by RequestsEndingIn4xx desc

// 5. Slowest model calls: total time versus time spent waiting for the backend
let backend = OTelSpans
| where TimeGenerated > ago(24h)
| where Name == "backend"
| project TraceId, BackendMs = DurationMs;
OTelSpans
| where TimeGenerated > ago(24h)
| where Kind =~ "Server" and tostring(Attributes["http.route"]) contains "/models/"
| project TimeGenerated, TraceId, Model = tostring(Attributes["gen_ai.request.model"]), TotalMs = DurationMs
| join kind=leftouter backend on TraceId
| extend GatewayMs = TotalMs - BackendMs
| project TimeGenerated, TraceId, Model, TotalMs, BackendMs, GatewayMs
| top 20 by TotalMs desc

// 6. MCP tool calls by tool name
OTelSpans
| where TimeGenerated > ago(24h)
| extend Operation = coalesce(tostring(Attributes["gen_ai.operation.name"]), tostring(Attributes["azure.ai_gateway.operation.name"]), tostring(Attributes["mcp.method.name"])),
         ToolName = tostring(Attributes["gen_ai.tool.name"])
| where Operation =~ "tools/call" or Name startswith "tools/call "
| where isnotempty(ToolName)
| summarize Calls = count(), Errors = countif(StatusCode =~ "Error") by ToolName
| order by Calls desc

// 7. Every span of one trace, in order (paste a trace ID from Monitoring › Traces)
let traceId = "<trace-id>";
OTelSpans
| where TimeGenerated > ago(30d)
| where TraceId == traceId
| project TimeGenerated, SpanId, ParentSpanId, Name, Kind, DurationMs, StatusCode,
          PolicyType = tostring(Attributes["azure.apim.policy.type"]), Attributes
| order by TimeGenerated asc

To run a query from the command line instead, pass the workspace's customer ID to az monitor log-analytics query.   'OTelSpans | where TimeGenerated > ago(1h) | where Kind =~ "Server" and tostring(Attributes["http.route"]) contains "/models/" | summarize Calls = count() by Model = tostring(Attributes["gen_ai.request.model"]), Status = toint(Attributes["http.response.status_code"])'

#Go further

  • Query the token metrics. Token and cost metrics land in the Azure Monitor workspace linked to Application Insights as azure.ai_gateway.client.token.usage and azure.ai_gateway.client.token.cost, with labels such as gen_ai.request.model and gen_ai.token.type. Docs show PromQL in its underscore form, for example sum by (gen_ai_request_model) (gen_ai_client_token_usage). Check which names your backend received before you build on them. Attribute tokens and cost with OpenTelemetry queries them.
  • Alert on what you can act on. Start with token usage spikes, backend authentication failures, and telemetry export failures. Route each alert to an owner who can investigate the gateway, backend, policy, or destination.
  • Send telemetry somewhere else. Use Custom OpenTelemetry destination to export to any OTLP endpoint. Store any credential headers as secrets.
  • Capture payloads carefully. Settings›Logging has Log request and response payloads. It's off by default because prompts and responses can be sensitive and add volume.
