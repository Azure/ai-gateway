Production & emerging · Lab 21

Deploy an enterprise reference architecture

Deploy a production-shaped AI Gateway environment from modular Bicep, with a keyless Foundry backend, models and MCP tools behind RBAC, a key per app, layered policies, and monitoring. Then promote it from dev to prod with a GitHub Actions workflow that signs in with OpenID Connect and smoke-tests every deployment.

Advanced 1 h Bicep Updated Oct 28, 2026
Source Edit

What you'll do

  • Explain the identity, policy, observability, and naming decisions behind a production AI Gateway deployment
  • Deploy a modular, subscription-scope Bicep template with separate parameter files for dev and prod
  • Layer gateway-wide baseline policies, applied by a merge-safe script, on top of model policies declared in Bicep
  • Automate preview, deployment, baselines, and a smoke test in GitHub Actions with OpenID Connect
  • Verify the model and MCP tool paths end to end, and clean up every resource

Before you start

  • 09Set gateway-wide policy baselines

  • 12Call backends with managed identities

Tracks: Bicep

You've built every piece by hand in earlier labs: a keyless Foundry backend, aliases, MCP servers, per-caller limits, a gateway-wide baseline, and monitoring. Now the platform team wants the whole setup as code. Dev and prod should differ only in their parameters, every change should go through a pull request, and a pipeline should deploy it without a stored secret. In this lab you deploy a modular reference architecture, apply the baseline, prove it works with a smoke test, and wire it all into GitHub Actions.

#Before you begin

  • Complete Set gateway-wide policy baselines, Monitor usage, cost, and traces, and Call backends with managed identities. This lab builds on what you learned there, not on the resources you created: it deploys a new, separate environment.
  • The Azure CLI↗ 2.75 or later, signed in with az login to the subscription you deploy to, and the aigateway extension (install it). The CLI installs Bicep the first time you deploy. You also need curl and jq (Bash) or PowerShell 7 or later. The smoke test reads the gateway and a key with the extension. The extension can't set gateway-scope policies yet, so the baseline script calls the management API with az rest.
  • Owner, or Contributor plus Role Based Access Control Administrator, on the subscription. The template creates two resource groups and several role assignments.
  • Quota for gpt-6-luna with the GlobalStandard SKU in the region you deploy to. The dev environment uses 50 capacity units (50,000 tokens per minute).
  • The resource providers Microsoft.ApiManagement, Microsoft.Web, Microsoft.CognitiveServices, Microsoft.OperationalInsights, and Microsoft.Insights registered on the subscription. Register any missing one with az provider register --namespace <namespace>.
  • For Automate deployments with GitHub Actions: a GitHub repository where you can create environments and variables, the GitHub CLI↗ signed in with gh auth login, and permission to create an app registration in Microsoft Entra ID.

#How it works

One subscription-scope template, infra/main.bicep, creates two resource groups and composes small modules. Each module owns one concern, so the people who own that concern can review and change it on their own, and no module outputs a secret. Parameter files hold everything that differs between environments.

Gateway-wide policies aren't in Bicep. They live on the gateway's default workspace, and declaring that workspace in a template would replace it. Instead, a script merges them in after each deployment, as in Set gateway-wide policy baselines.

#Make the architecture decisions

Each decision below is already built into the templates. In your own environment, change the parameters first, and change the shape only when your organization needs something different.

#Identity: no secrets between services or in the pipeline

Each trust boundary uses its own mechanism, and none of them needs a stored secret:

BoundaryMechanismWhere
Gateway to FoundryThe gateway's system-assigned identity has Foundry User on the account. The account sets disableLocalAuth: true, so Foundry keys don't work at all.gateway.bicep, foundry.bicep
Apps to gatewayOne runtime API key per app, so every app gets its own policy counters, its own row in Monitoring, and its own rotation. Or keyless Microsoft Entra calls through AI Gateway Models User on the alias and AI Gateway Tools User on the MCP server, granted to groups.keys.bicep, models.bicep, tools.bicep
Pipeline to AzureAn OpenID Connect federated credential. GitHub exchanges a short-lived token for an Azure token, so there's no client secret to rotate or leak.deploy-workflow.yml

Roles are granted at the narrowest scope that works: the alias instead of the whole gateway, and one MCP server instead of every tool. Templates output key names only, never key values. The smoke test reads a key with az aigateway api-key list-secrets when it needs one.

#Policies: a gateway floor plus model limits

LayerDeclared inPoliciesCounted per
Gatewaybaselines.json, applied by scripts/apply-baselines.shRequest rate limit: 120 calls per 60 seconds, on models and MCP servers. Cost limit: $20 per day, one budget across all models.Caller identity
Modelmodels.bicepToken rate limit: 20,000 tokens per minute in dev. Content safety: Balanced (Medium) for all four categories.Caller identity

The gateway evaluates every applicable policy before it forwards a request, and any one of them can block it. The platform team owns the gateway floor, and app teams tune the model layer through parameters. Blocked calls get 429 from a rate limit, 403 with LlmCostQuotaExceeded from the cost limit, and 400 from content safety.

The baseline script reads the workspace's policies array, updates policies of the same type in place, appends missing ones, and writes the array back with PATCH. Updating in place keeps a cost limit's id, its portal-only overrides, and the spend it has already counted.

Note

The portal writes "scope": "workspace" on Gateway scope rate and cost limits, so baselines.json does too. If the API rejects a field, create the policy once in the portal at Gateway scope, read the workspace with az rest, and copy that shape into baselines.json.

#Observability: the destination in Bicep, the connection in the portal

monitoring.bicep creates the Log Analytics workspace and the Application Insights component, with retention set per environment. The sample also declares a telemetry exporter of kind applicationInsights, but the current portal treats that kind as legacy: it no longer activates the OTLP signals the Monitoring dashboard needs. The OpenTelemetry exporter that replaces it isn't documented for automation yet. So you connect the component once in the portal after the first deployment. No module declares an exporter, so later deployments leave that connection alone. The sample's exporter is still available as telemetry.bicep, behind enableLegacyAppInsightsExporter.

#Naming, tags, and resource groups

  • Deterministic names. A resource token, the first eight characters of uniqueString(subscription, environmentName, location), goes into every name. Deploying again updates the same resources instead of creating new ones.
  • Two resource groups. rg-<env>-<token>-gateway holds the gateway and its monitoring, and rg-<env>-<token>-foundrymodels holds model capacity. You can secure, scale, and delete them separately, and only the gateway's identity needs access to Foundry.
  • A unique gateway name. The gateway is aigw-<token>, which becomes https://aigw-<token>.<region>-01.ai.gateway.azure.com. Set aiGatewayName to choose your own: up to 24 letters, digits, and hyphens, starting with a letter.
  • Tags. Resource groups and top-level resources get environment and workload: ai-gateway, plus the tags from the parameter file, such as costCenter.
  • Regions. aiGatewayLocation defaults to eastus2. Set it to any region where AI Gateway is available, as in Find the available regions. The other resources follow the deployment's --location, so pick one where the model is available.

Tip

Put prod in its own subscription so quotas, role assignments, and Azure Policy stay isolated from dev. The template is subscription-scoped, so it works unchanged. Use a separate deployment identity for each subscription.

#Delivery: GitHub Actions with OpenID Connect

The workflow installs the aigateway extension, previews every change with what-if, deploys, applies the baseline, and runs the smoke test. A prod GitHub environment with required reviewers gates production, and a concurrency group per environment stops two runs from deploying to the same environment at once. The deployment identity needs Contributor and Role Based Access Control Administrator on the subscription, because the template creates role assignments. To narrow that, you can add a condition that only lets it assign the roles the template needs, as described in Delegate Azure access management to others↗.

#Review the templates

main.bicep wires the modules together and passes outputs from one to the next, so Bicep deploys them in the right order: monitoring and Foundry first, then the gateway, then models, tools, and keys.

// Enterprise reference deployment for Azure AI Gateway. One subscription-scope template creates two resource groups
// and composes small modules:
//
//   rg-<env>-<token>-foundrymodels   foundry.bicep         Foundry account (keyless) + model deployment
//   rg-<env>-<token>-gateway         monitoring.bicep      Log Analytics + Application Insights
//                                    gateway.bicep         aigateways resource + connector gateway + Foundry User role for the gateway identity
//                                    models.bicep          Foundry provider + backend model (tokenLimit, contentSafety) + alias
//                                    tools.bicep           Microsoft Learn MCP server
//                                    keys.bicep            one runtime API key per app
//                                    telemetry.bicep       optional legacy exporter (off by default)
//
// Gateway-wide baseline policies are applied after deployment by scripts/apply-baselines.sh (or .ps1).

Warning

Each deployment sends a PUT for the gateway with exactly the properties in gateway.bicep. If you change gateway settings outside Bicep, add them to this module. Otherwise, the next deployment can reset them. Outbound virtual network integration is the exception: you can set it only when the gateway is created. gateway.bicep accepts it as backendSubnetId, but main.bicep doesn't pass it. To use it, add a parameter to main.bicep before the first deployment and keep passing the same subnet on every later deployment. See Lock down backend traffic with private networking.

#!/usr/bin/env bash
# Applies the gateway-wide baseline policies in infra/baselines.json to an AI Gateway.
#
# Gateway-scope policies live in the policies array of the gateway's default workspace. A PATCH replaces the whole
# array, so the script reads the current array, merges the baselines into it, and writes it back:
#   - A baseline whose type already exists updates that policy in place and keeps its id, overrides, and any other
#     fields you set in the portal. Updating a costLimit this way keeps its accumulated spend.
#   - A baseline whose type doesn't exist is appended. A new costLimit gets a fresh, stable id.
#   - Policies of other types (for example ones you added in the portal) are left untouched.
# Running it twice gives the same result. The aigateway CLI extension can't set gateway-scope policies yet, so the
# script calls the management API with az rest.
#
# Usage:
#   export RG="<gateway-resource-group>" GATEWAY="<gateway-name>"
#   ./apply-baselines.sh [baselines.json]
#   DRY_RUN=1 ./apply-baselines.sh          # print the merged array without changing anything
#
# Requires Azure CLI and jq.
set -euo pipefail

SCRIPT_DIR="$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)"
BASELINES="${1:-$SCRIPT_DIR/../baselines.json}"
API_VERSION="2025-09-01-preview"
: "${RG:?Set RG to the gateway resource group}"
: "${GATEWAY:?Set GATEWAY to the gateway name}"
command -v jq >/dev/null || { echo "This script needs jq." >&2; exit 1; }
jq -e 'type == "array" and all(.[]; has("type"))' "$BASELINES" >/dev/null \
  || { echo "$BASELINES must be a JSON array of policy objects." >&2; exit 1; }

SUB="$(az account show --query id -o tsv)"
URL="https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.ApiManagement/aigateways/$GATEWAY/workspaces/default?api-version=$API_VERSION"
NEW_ID="$( (uuidgen 2>/dev/null || cat /proc/sys/kernel/random/uuid) | tr 'A-Z' 'a-z')"

CURRENT="$(az rest --method get --url "$URL")"
POLICIES="$(printf '%s' "$CURRENT" | jq -c --slurpfile base "$BASELINES" --arg id "$NEW_ID" '
  reduce $base[0][] as $b (.properties.policies // [];
    if any(.[]; .type == $b.type)
    then map(if .type == $b.type then . + $b else . end)
    else . + [if $b.type == "costLimit" and ($b.id // "") == "" then $b + {id: $id} else $b end]
    end)')"

echo "Gateway-scope policies after merge:"
printf '%s' "$POLICIES" | jq .

if [ "${DRY_RUN:-0}" = "1" ]; then
  echo "DRY_RUN=1: nothing was changed."
  exit 0
fi

az rest --method patch --url "$URL" --body "{\"properties\":{\"policies\":$POLICIES}}" --output none
echo "Applied. Current gateway-scope policy types:"
az rest --method get --url "$URL" --query "properties.policies[].type" -o tsv

On GitHub, open infra/scripts/apply-baselines.sh↗ or infra/scripts/apply-baselines.ps1↗.

requestRateLimit
costLimit
