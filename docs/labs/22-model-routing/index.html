Route an alias across models by priority and weight

Put two Foundry models behind one alias, canary a new model version with an 80/20 weighted split, then prefer one model by priority, all without changing the model name that clients send.

Intermediate 25 min PortalCLIBicep Updated Oct 28, 2026
Source Edit

What you'll do

  • Explain how priority and weight decide which backend model serves a request
  • Put two backend models behind one alias with an 80/20 weighted split
  • Tell which backend model served each request from the response
  • Prefer one backend model by priority, then promote the other without changing clients

Before you start

  • 02Publish a Foundry model and make your first call

Tracks: Portal, Azure CLI, Bicep + azd

Your team wants to try gpt-6.1-sol, but every app already sends "model": "chat", and nobody wants a big-bang switch. In this lab you put the current model and the new one behind the same alias, send a fifth of the traffic to the new model, count where the requests land, and then use priority to choose which model is preferred. The apps never change the model name they send.

#How it works

An alias holds a list of backend models. Each one has a priority and a weight:

SettingValuesDefaultWhat it does
PriorityWhole number from 0 to 1000Lower numbers are preferred. Requests go to the backend models with the lowest priority number.
WeightWhole number from 1 to 1001Splits traffic among the backend models that share a priority, in proportion to their weights.

A backend model's Share within priority is its weight divided by the sum of the weights at its priority. Weights 80 and 20 give 80% and 20%; weights 3 and 1 give 75% and 25%. With one backend model, the alias behaves like the single-target aliases of labs 02 and 03.

Pick the values from the job you need to do:

ScenarioPriorityWeight
Canary a new model versionSame for bothSmall share for the new version, for example 95 and 5, then raise it
A/B test two modelsSame for bothEqual, for example 50 and 50
Balance deployments across regions or providersSame for allIn proportion to each deployment's capacity, for example 3 and 1
Prefer purchased capacityProvisioned deployment 0, pay-as-you-go 1Any

A few rules keep every request answerable:

  • Each backend model can appear only once in an alias.
  • All backend models must support at least one interface in common, for example OpenAI Chat Completions. Mixing an Anthropic Messages model with an OpenAI model in one alias fails.
  • The response tells you which backend served the request: the model field holds the backend's model name and version, for example gpt-6.1-sol-2026-09-29, and Foundry models also return an x-ms-served-model header.
Important

Priority sets a preference, not a guaranteed failover. In our tests, when the preferred backend returned an error such as 429 or 404, the gateway passed that error to the client instead of retrying a lower-priority backend. Test how your gateway behaves under throttling before you rely on priority for availability, and keep retries in your clients.

#Create the chat alias

Each --backend-model adds an entry to the alias's backendModels list, with a resource-id, a priority, and a weight. With more than one backend model, each entry needs both a priority and a weight.

# Build the resource ID prefix of the provider's backend models, which each --backend-model entry uses
export MODELS="$GATEWAY_ID/workspaces/default/modelProviders/$PROVIDER/models"

# Create or update the alias with both backend models at priority 0 and weights 80 and 20, then print the routing
echo "🔖 Alias $ALIAS routes to:"
az aigateway model-alias set -g "$RG" --gateway-name "$GATEWAY" -n "$ALIAS" \
  --description "Canary: 80/20 between the current and the new model" \
  --backend-model resource-id="$MODELS/$PRIMARY" priority=0 weight=80 \
  --backend-model resource-id="$MODELS/$CANDIDATE" priority=0 weight=20 \
  --only-show-errors --query properties.backendModels -o json |
  jq -r '.[] | "\(.resourceId | split("/") | last)  priority \(.priority)  weight \(.weight)"'
# Build the resource ID prefix of the provider's backend models, which each --backend-model entry uses
$MODELS = "$GATEWAY_ID/workspaces/default/modelProviders/$PROVIDER/models"

# Create or update the alias with both backend models at priority 0 and weights 80 and 20, then print the routing
Write-Host "🔖 Alias $ALIAS routes to:"
az aigateway model-alias set -g $RG --gateway-name $GATEWAY -n $ALIAS `
  --description "Canary: 80/20 between the current and the new model" `
  --backend-model resource-id="$MODELS/$PRIMARY" priority=0 weight=80 `
  --backend-model resource-id="$MODELS/$CANDIDATE" priority=0 weight=20 `
  --only-show-errors --query properties.backendModels -o json |
  ConvertFrom-Json | ForEach-Object { '{0}  priority {1}  weight {2}' -f ($_.resourceId -split '/')[-1], $_.priority, $_.weight }

az aigateway model-alias set creates the alias, or updates it if it exists, so you can run the step again.

Checkpoint

@maxLength(60)

infra/alias-routing.bicep registers the candidate deployment under the existing provider and publishes the alias. It only references gpt-6-luna, so that model's settings stay as they are. Its strategy parameter switches between a weighted split and a priority preference. You can also deploy it on its own to the gateway from lab 02:

infra/alias-routing.bicepGitHub
// Routes one callable alias across two Foundry backend models. main.bicep calls it after the quick start's template,
// and you can also deploy it on its own to a gateway you already have, such as the one from lab 02.
// Registers a candidate deployment under the existing Foundry provider, then publishes an alias that either splits
// traffic between the primary and the candidate by weight, or prefers the primary by priority.
// The primary backend model is only referenced, so its policies stay untouched.
targetScope = 'resourceGroup'

@description('Name of the existing AI Gateway (Microsoft.ApiManagement/aigateways) in this resource group.')
param gatewayName string

@description('Name of the existing Foundry model provider in the gateway, for example foundry-models from lab 02.')
param providerName string = 'foundry-models'

@description('Name of the existing backend model that takes most of the traffic, for example gpt-6-luna.')
param primaryModelName string = 'gpt-6-luna'

@description('Resource ID of the Foundry account that hosts the candidate deployment.')
param foundryAccountId string

@description('Name of the candidate deployment in that account, for example gpt-6.1-sol.')
param candidateDeploymentName string = 'gpt-6.1-sol'

@description('Version of the candidate model, for example 2026-09-29. Optional.')
param candidateModelVersion string = ''

@description('Callable alias that clients send in the request "model" field.')
param aliasName string = 'chat'

@description('weighted: both backends share priority 0 and split traffic by weight. priority: the primary is preferred, and the candidate gets priority 1.')
@allowed([
  'weighted'
  'priority'
])
param strategy string = 'weighted'

@description('Weighted strategy only: the candidate weight. The primary gets 100 minus this value.')
@minValue(1)
@maxValue(99)
param candidateWeight int = 20

type route = {
  @description('Resource ID of the backend model.')
  resourceId: string

  @description('Lower numbers are preferred. 0 to 100.')
  @minValue(0)
  @maxValue(100)
  priority: int

  @description('Share of traffic among backends with the same priority. 1 to 100.')
  @minValue(1)
  @maxValue(100)
  weight: int
}

#disable-next-line BCP081
resource aiGateway 'Microsoft.ApiManagement/aigateways@2025-09-01-preview' existing = {
  name: gatewayName
}

#disable-next-line BCP081
resource defaultWorkspace 'Microsoft.ApiManagement/aigateways/workspaces@2025-09-01-preview' existing = {
  parent: aiGateway
  name: 'default'
}

#disable-next-line BCP081
resource provider 'Microsoft.ApiManagement/aigateways/workspaces/modelProviders@2025-09-01-preview' existing = {
  parent: defaultWorkspace
  name: providerName
}

#disable-next-line BCP081
resource primary 'Microsoft.ApiManagement/aigateways/workspaces/modelProviders/models@2025-09-01-preview' existing = {
  parent: provider
  name: primaryModelName
}

#disable-next-line BCP081
resource candidate 'Microsoft.ApiManagement/aigateways/workspaces/modelProviders/models@2025-09-01-preview' = {
  parent: provider
  name: candidateDeploymentName
  properties: {
    displayName: candidateDeploymentName
    description: 'Candidate deployment that the ${aliasName} alias routes to.'
    apiFormat: 'OpenAIChatCompletions'
    supportedEndpoints: [
      '/openai/v1/chat/completions'
      '/openai/v1/responses'
    ]
    deployment: {
      resourceId: '${foundryAccountId}/deployments/${candidateDeploymentName}'
      modelName: candidateDeploymentName
      modelVersion: empty(candidateModelVersion) ? null : candidateModelVersion
    }
  }
}

var routes route[] = strategy == 'weighted'
  ? [
      { resourceId: primary.id, priority: 0, weight: 100 - candidateWeight }
      { resourceId: candidate.id, priority: 0, weight: candidateWeight }
    ]
  : [
      { resourceId: primary.id, priority: 0, weight: 1 }
      { resourceId: candidate.id, priority: 1, weight: 1 }
    ]

#disable-next-line BCP081
resource alias 'Microsoft.ApiManagement/aigateways/workspaces/aliases@2025-09-01-preview' = {
  parent: defaultWorkspace
  name: aliasName
  properties: {
    description: strategy == 'weighted'
      ? 'Splits traffic ${100 - candidateWeight}/${candidateWeight} between ${primaryModelName} and ${candidateDeploymentName}.'
      : 'Prefers ${primaryModelName}. ${candidateDeploymentName} has a lower preference.'
    backendModels: [
      for r in routes: {
        resourceId: r.resourceId
        priority: r.priority
        weight: r.weight
      }
    ]
  }
}

output aliasName string = alias.name
output candidateModelName string = candidate.name
output routes array = [
  for r in routes: {
    model: last(split(r.resourceId, '/'))
    priority: r.priority
    weight: r.weight
  }
]
output chatCompletionsUrl string = 'https://${aiGateway.properties.frontend.defaultHostname}/default/models/openai/v1/chat/completions'

#Go further

  • Canary in steps. Move the weights from 95/5 to 80/20 to 50/50 while you watch errors, latency, and cost per model in Monitor usage, cost, and traces. Weights must be at least 1, so to stop sending traffic to a model, give it a higher priority number or remove it from the alias.
  • Prefer provisioned throughput. Put a provisioned deployment at priority 0 and a pay-as-you-go deployment of the same model at priority 1, so purchased capacity is used first. Test what happens when the provisioned deployment is saturated before you depend on it.
  • Balance regions or providers. Register the same model from two Foundry accounts, or from Foundry and a custom provider, and give them weights in proportion to their quota.
  • Limit each model and the alias. A token limit on a backend model, as in Throttle tokens per caller with token limits, applies to that model. A limit on the alias applies to every request that calls chat.
