Publish a Foundry model and make your first call

Publish a Microsoft Foundry model deployment through your gateway with its managed identity, create a runtime API key, try the model in the Catalog playground, and call it from curl, PowerShell, Python, TypeScript, and C#.

Beginner 25 min PortalCLIBicepCode Updated Oct 28, 2026
Notebook Source Edit

What you'll do

  • Publish a Foundry model deployment through the gateway, authenticated with the gateway's managed identity
  • Create a runtime API key and keep its value out of code
  • Call the model through the gateway with the Chat Completions and Responses APIs
  • Explain what the gateway does with a request between your app and the model

Before you start

  • 01Provision your AI Gateway

Tracks: Portal, Azure CLI, Bicep + azd, Code

The first product team wants to use gpt-6-luna, which already runs in your Microsoft Foundry account. You don't want to hand every team the Foundry endpoint and a provider key. In this lab you publish the deployment through your gateway, give the team a runtime API key of its own, and make the first call from the playground, a shell, and code. The gateway authenticates to Foundry with its own managed identity, so the app never sees a Foundry credential.

#How it works

Publishing a model has three parts. A model provider tells the gateway where the Foundry account is and how to authenticate to it. A backend model registers one deployment under that provider. A callable alias is the stable name that clients send in the request model field. Importing from Foundry creates all three for you.

Clients call one runtime URL with a gateway API key. The gateway validates the key before anything else, runs the policies that apply, swaps the caller's key for its own managed identity token, and forwards the request unchanged to Foundry. The response comes back as is, and the gateway records token usage for monitoring.

StepWhat happensWhere you set it
Inbound authenticationAn active runtime key in the api-key header, or as Authorization: Bearer <key> (what the OpenAI SDKs send), or the call fails with 401Access›Keys
Routing/default/models/openai/v1/chat/completions or /responses, and model must equal an aliasModel details and its Aliases tab
PoliciesToken limits, cost limits, and content safety run before the backend callPolicies (labs 06–09)
Backend authenticationThe gateway's managed identity, with the Foundry User role on the accountModel provider
TelemetryTokens, latency, and the API key that made the callMonitoring (lab 13)

#Import the deployment from Foundry

  1. Open the AI Gateway portal↗ and select your gateway in the top bar.
  2. Select Models›Add›Models from Microsoft Foundry. (On Home, Add from Microsoft Foundry in the Set up your gateway guide starts the same import.)
  3. Select the subscription and resource group of your Foundry account. The wizard discovers the deployments automatically. Deployments that are already in this gateway can't be selected again.
  4. Select the gpt-6-luna deployment and keep Managed identity as the Authentication method.
  5. Under Aliases, keep Create an alias for each model selected, then select Add models.
Note

The gateway calls Foundry with its system-assigned managed identity, which needs the Foundry User role on the account. If your first call returns 403 from the backend, assign the role yourself and wait a few minutes for it to take effect:

Bash
# Read the principal ID of the gateway's managed identity, and the Foundry account's resource ID
PRINCIPAL_ID="$(az aigateway show -g "$RG" -n "$GATEWAY" --query identity.principalId -o tsv)"
FOUNDRY_ID="$(az cognitiveservices account show -g "$FOUNDRY_RG" -n "$FOUNDRY_ACCOUNT" --query id -o tsv)"
echo "👤 Gateway identity: $PRINCIPAL_ID"

# Give the gateway's identity the Foundry User role on the account, so that it can call the model
az role assignment create --assignee-object-id "$PRINCIPAL_ID" --assignee-principal-type ServicePrincipal \
  --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" --scope "$FOUNDRY_ID" --output none &&
  echo "🔐 The gateway's identity has the Foundry User role on $FOUNDRY_ACCOUNT"

#Grant the gateway access to the account

The portal import does three things for you: it grants the gateway's identity access to the account, creates the provider, and registers the deployments. From the command line, you do each step yourself. First, give the gateway's system-assigned identity the Foundry User role on the account.

# Read the principal ID of the gateway's system-assigned managed identity
PRINCIPAL_ID="$(az aigateway show -g "$RG" -n "$GATEWAY" --query identity.principalId -o tsv)"
echo "👤 Gateway identity: $PRINCIPAL_ID"

# Give the identity the Foundry User role on the account, so that the gateway can call its deployments
az role assignment create --assignee-object-id "$PRINCIPAL_ID" --assignee-principal-type ServicePrincipal \
  --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" --scope "$FOUNDRY_ID" --query id -o tsv &&
  echo "🔐 The gateway's identity has the Foundry User role on $FOUNDRY_ACCOUNT"
# Read the principal ID of the gateway's system-assigned managed identity
$PRINCIPAL_ID = az aigateway show -g $RG -n $GATEWAY --query identity.principalId -o tsv
Write-Host "👤 Gateway identity: $PRINCIPAL_ID"

# Give the identity the Foundry User role on the account, so that the gateway can call its deployments
az role assignment create --assignee-object-id $PRINCIPAL_ID --assignee-principal-type ServicePrincipal `
  --role "53ca6127-db72-4b80-b1b0-d745d6d5456d" --scope $FOUNDRY_ID --query id -o tsv

#Create the Foundry provider

The provider tells the gateway where the account is and to authenticate with its managed identity.

# Create a Foundry provider that points at the account and signs in with the gateway's managed identity
az aigateway model-provider create -g "$RG" --gateway-name "$GATEWAY" -n "$PROVIDER" \
  --kind Foundry --display-name "Foundry models" \
  --foundry "{endpoint:'$FOUNDRY_ENDPOINT',resourceIds:[$FOUNDRY_ID],authentication:{kind:ManagedIdentity,managedIdentity:{resource:'https://cognitiveservices.azure.com/'}}}" \
  --query "{name:name, kind:properties.kind, endpoint:properties.foundry.endpoint}" &&
  echo "🔌 Model provider $PROVIDER points at $FOUNDRY_ACCOUNT"
# Create a Foundry provider that points at the account and signs in with the gateway's managed identity
az aigateway model-provider create -g $RG --gateway-name $GATEWAY -n $PROVIDER `
  --kind Foundry --display-name "Foundry models" `
  --foundry "{endpoint:'$FOUNDRY_ENDPOINT',resourceIds:[$FOUNDRY_ID],authentication:{kind:ManagedIdentity,managedIdentity:{resource:'https://cognitiveservices.azure.com/'}}}" `
  --query "{name:name, kind:properties.kind, endpoint:properties.foundry.endpoint}"
if ($?) { Write-Host "🔌 Model provider $PROVIDER points at $FOUNDRY_ACCOUNT" }
4

#Register the deployment

A backend model registers one deployment under the provider. Name it after the deployment.

# Register the deployment as a backend model under the provider, with the endpoints that apps can call
az aigateway model create -g "$RG" --gateway-name "$GATEWAY" --provider-name "$PROVIDER" -n "$DEPLOYMENT" \
  --display-name "$DEPLOYMENT" --api-format OpenAIChatCompletions \
  --supported-endpoints /openai/v1/chat/completions /openai/v1/responses \
  --deployment-config "{resourceId:$FOUNDRY_ID/deployments/$DEPLOYMENT,modelName:$DEPLOYMENT}" \
  --query "{name:name, deployment:properties.deployment.modelName}" &&
  echo "✨ Model $DEPLOYMENT is registered under $PROVIDER"
# Register the deployment as a backend model under the provider, with the endpoints that apps can call
az aigateway model create -g $RG --gateway-name $GATEWAY --provider-name $PROVIDER -n $DEPLOYMENT `
  --display-name $DEPLOYMENT --api-format OpenAIChatCompletions `
  --supported-endpoints /openai/v1/chat/completions /openai/v1/responses `
  --deployment-config "{resourceId:$FOUNDRY_ID/deployments/$DEPLOYMENT,modelName:$DEPLOYMENT}" `
  --query "{name:name, deployment:properties.deployment.modelName}"
if ($?) { Write-Host "✨ Model $DEPLOYMENT is registered under $PROVIDER" }

--deployment-config uses the Azure CLI shorthand syntax, so the same value works in Bash and PowerShell.

To publish more deployments, repeat this step and the next one for each name that az cognitiveservices account deployment list -g "$FOUNDRY_RG" -n "$FOUNDRY_ACCOUNT" --query "[].name" -o tsv returns.

Tip

az aigateway model create --foundry-resource-id "$FOUNDRY_ID" --deployment "$DEPLOYMENT" does the last three steps in one command, like the portal import: it grants the gateway's identity Foundry User on the account, creates a provider named after the account, and registers the deployment. You can run it again safely. It doesn't publish an alias, so you still run the next step. This lab creates each piece itself so you see how they fit together.

#Publish an alias

Clients send an alias in the request model field, not the backend model name. Publish one named after the deployment that points at the model you registered.

# Name the alias after the deployment, and build the resource ID of the model that it points at
export AI_GATEWAY_MODEL="$DEPLOYMENT"
MODEL_ID="$GATEWAY_ID/workspaces/default/modelProviders/$PROVIDER/models/$DEPLOYMENT"

# Publish the alias, or update it if it exists, and print its name and the model that it points at
az aigateway model-alias set -g "$RG" --gateway-name "$GATEWAY" -n "$AI_GATEWAY_MODEL" \
  --backend-model resource-id="$MODEL_ID" \
  --query "{alias:properties.aliasName, target:properties.backendModels[0].resourceId}" &&
  echo "🔖 Alias $AI_GATEWAY_MODEL is ready"
# Name the alias after the deployment, and build the resource ID of the model that it points at
$env:AI_GATEWAY_MODEL = $DEPLOYMENT
$MODEL_ID = "$GATEWAY_ID/workspaces/default/modelProviders/$PROVIDER/models/$DEPLOYMENT"

# Publish the alias, or update it if it exists, and print its name and the model that it points at
az aigateway model-alias set -g $RG --gateway-name $GATEWAY -n $env:AI_GATEWAY_MODEL `
  --backend-model resource-id="$MODEL_ID" `
  --query "{alias:properties.aliasName, target:properties.backendModels[0].resourceId}"
if ($?) { Write-Host "🔖 Alias $env:AI_GATEWAY_MODEL is ready" }

az aigateway model-alias set creates the alias, or updates it if it exists, so you can run the step again. When it creates the alias, it warns that the service doesn't enforce atomic alias creation. That's expected: it only matters when two people create the same alias at the same time.

#Create a runtime API key

#Review the templates

infra/main.bicep creates the resource group rg-<environment name> and composes three templates. It calls lab 01's gateway.bicep↗ for the gateway, infra/foundry.bicep for the Foundry account and its gpt-6-luna deployment, and then infra/publish-model.bicep to publish the deployment through the gateway:

infra/main.bicepGitHub
// Lab 02 with azd: "azd up" creates the resource group rg-<environment name> with lab 01's gateway and this lab's
// Foundry account and gpt-6-luna deployment, then publishes the deployment through the gateway: the Foundry User
// role, the model provider, the backend model, the alias, and the app-first-call key.
// The runtime API key is never an output.
targetScope = 'subscription'

@description('azd environment name. The resource group is rg-<environmentName>.')
@minLength(1)
@maxLength(60)
param environmentName string

@description('Region for every resource. Pick one where AI Gateway and the lab\'s Foundry models are available. List them with az provider show --namespace Microsoft.ApiManagement (Setup guide, Find the available regions).')
@metadata({ azd: { type: 'location' } })
param location string

@description('Tokens per minute that each caller identity can use on the model. azd reads it from TOKENS_PER_MINUTE.')
@minValue(1)
param tokensPerMinute int = 10000

var suffix = take(uniqueString(subscription().id, environmentName, location), 6)
var tags = { 'azd-env-name': environmentName }

resource rg 'Microsoft.Resources/resourceGroups@2024-03-01' = {
  name: 'rg-${environmentName}'
  location: location
  tags: tags
}

// Lab 01's template: the gateway with a system-assigned identity, and its connector gateway.
module gateway '../../01-provision-gateway/infra/gateway.bicep' = {
  name: 'aigw-gateway'
  scope: rg
  params: {
    gatewayName: 'aigw-${suffix}'
    location: location
    tags: tags
  }
}

// The backend: a Foundry account with a gpt-6-luna deployment.
module foundry 'foundry.bicep' = {
  name: 'aigw-foundry'
  scope: rg
  params: {
    accountName: 'aigw${suffix}'
    location: location
    tags: tags
  }
}

// The Foundry User role for the gateway, then the provider, the backend model, the alias, and the key.
module publish 'publish-model.bicep' = {
  name: 'aigw-publish-model'
  scope: rg
  params: {
    gatewayName: gateway.outputs.gatewayName
    foundryAccountId: foundry.outputs.accountId
    deploymentName: foundry.outputs.deploymentName
    tokensPerMinute: tokensPerMinute
  }
}

output AZURE_RESOURCE_GROUP string = rg.name
output AI_GATEWAY_NAME string = gateway.outputs.gatewayName
output AI_GATEWAY_ID string = gateway.outputs.gatewayId
output AI_GATEWAY_URL string = gateway.outputs.gatewayUrl
output AI_GATEWAY_PROVIDER string = publish.outputs.providerName
output AI_GATEWAY_BACKEND_MODEL string = publish.outputs.modelName
output AI_GATEWAY_MODEL string = publish.outputs.aliasName
output AI_GATEWAY_API_KEY_NAME string = publish.outputs.apiKeyName
output FOUNDRY_ACCOUNT_NAME string = foundry.outputs.accountName

infra/foundry.bicep creates an Azure AI Services account with local key authentication disabled, and a gpt-6-luna GlobalStandard deployment. Skip it in your own templates if you already have a deployment:

infra/foundry.bicepGitHub
// Optional: creates a Microsoft Foundry (Azure AI Services) account with one gpt-6-luna deployment
// to use as the backend for this lab. Skip it if you already have a Foundry or Azure OpenAI deployment.
// Mirrors infra/foundry-models/main.bicep in the reference sample. Model inference is billed.
// The lab's main.bicep calls it with azd. You can also deploy it on its own with "az deployment group create".
targetScope = 'resourceGroup'

@description('Foundry account name. It is also used as the custom subdomain, so it must be globally unique.')
@minLength(2)
@maxLength(64)
param accountName string

@description('Region for the Foundry account. The model and SKU must be available in this region.')
param location string = resourceGroup().location

@description('Name of the model deployment that the gateway will publish.')
param deploymentName string = 'gpt-6-luna'

@description('Model to deploy.')
param modelName string = 'gpt-6-luna'

@description('Model version to deploy.')
param modelVersion string = '2026-09-22'

@description('Deployment SKU.')
param skuName string = 'GlobalStandard'

@description('Deployment capacity in thousands of tokens per minute.')
@minValue(1)
param capacity int = 10

@description('Tags applied to the account.')
param tags object = {}

resource account 'Microsoft.CognitiveServices/accounts@2025-04-01-preview' = {
  name: accountName
  location: location
  tags: tags
  kind: 'AIServices'
  sku: {
    name: 'S0'
  }
  identity: {
    type: 'SystemAssigned'
  }
  properties: {
    allowProjectManagement: false
    customSubDomainName: toLower(accountName)
    disableLocalAuth: true
    networkAcls: {
      defaultAction: 'Allow'
      virtualNetworkRules: []
      ipRules: []
    }
    publicNetworkAccess: 'Enabled'
  }
}

resource deployment 'Microsoft.CognitiveServices/accounts/deployments@2025-04-01-preview' = {
  parent: account

#Run both calls with a script

The script prints the HTTP status and the reply for each interface, which makes failures easier to read.

infra/call-model.shGitHub
#!/usr/bin/env bash
# Calls a model through AI Gateway twice, once with Chat Completions and once with the Responses API,
# and prints the HTTP status and the model's reply for each call.
#
# Usage:
#   export AI_GATEWAY_URL="https://<gateway>.eastus2-01.ai.gateway.azure.com"
#   export AI_GATEWAY_MODEL="<model-alias>"
#   export AI_GATEWAY_API_KEY="..."      # never commit this value
#   ./call-model.sh ["Your prompt"]
# Requires curl and jq.
set -euo pipefail

PROMPT="${1:-Write a one-sentence status update.}"
: "${AI_GATEWAY_URL:?Set AI_GATEWAY_URL to https://<gateway>.eastus2-01.ai.gateway.azure.com}"
: "${AI_GATEWAY_MODEL:?Set AI_GATEWAY_MODEL to the callable model alias}"
: "${AI_GATEWAY_API_KEY:?Set AI_GATEWAY_API_KEY to a runtime key from Access > Keys}"

BASE="${AI_GATEWAY_URL%/}/default/models/openai/v1"

call() {
  local label="$1" path="$2" body="$3" filter="$4" out status reply
  out=$(curl -sS -w '\n%{http_code}' "$BASE$path" \
    -H "api-key: $AI_GATEWAY_API_KEY" -H "Content-Type: application/json" -d "$body")
  status="${out##*$'\n'}"
  reply="${out%$'\n'*}"
  if [[ "$status" == 2* ]]; then
    printf '%-17s HTTP %s  %s\n' "$label" "$status" "$(printf '%s' "$reply" | jq -r "$filter")"
  else
    printf '%-17s HTTP %s  %s\n' "$label" "$status" "$reply"
  fi
}

call "Chat Completions" "/chat/completions" \
  "$(jq -n --arg m "$AI_GATEWAY_MODEL" --arg p "$PROMPT" '{model:$m, messages:[{role:"user", content:$p}]}')" \
  '.choices[0].message.content'

call "Responses API" "/responses" \
  "$(jq -n --arg m "$AI_GATEWAY_MODEL" --arg p "$PROMPT" '{model:$m, input:$p}')" \
  '[.output[]? | select(.type == "message") | .content[]? | select(.type == "output_text") | .text] | join("")'

#Call the model from code

The OpenAI SDKs send their API key as Authorization: Bearer <key>, which the model endpoint accepts, so the runtime key goes straight into the SDK. Don't also add an api-key default header: the gateway rejects a request that has both with 400. The .NET sample uses HttpClient, like the .NET samples in the AI Gateway docs, so it sends the api-key header explicitly.

import os

from openai import OpenAI

gateway_url = os.environ["AI_GATEWAY_URL"].rstrip("/")

)

response = client.responses.create(model=model, input="Write a one-sentence status update.")
print(f"Responses API:    {response.output_text}")

completion = client.chat.completions.create(
    model=model,
    messages=[{"role": "user", "content": "Describe an AI gateway in one sentence."}],
)
print(f"Chat Completions: {completion.choices[0].message.content}")

  • Publish models from other providers. Put OpenAI, Anthropic, AWS Bedrock, or Google Vertex AI models behind the same gateway in Publish models from any provider behind stable aliases.

#Delete what you published

When you're done with the labs, delete the key, the alias, and the provider, then remove the role assignment that the gateway received on the Foundry account. Delete the alias first: deleting the provider also deletes its models, but not the aliases that point at them. Deleting a model from the gateway doesn't delete the Foundry deployment. The commands use the names from the CLI track. If you imported in the portal, use the provider and alias names shown on Models.

  echo "🚮 API key app-first-call is deleted"

  echo "🚮 Alias $DEPLOYMENT is deleted"

az aigateway model-provider delete -g "$RG" --gateway-name "$GATEWAY" -n "$PROVIDER" --yes &&
  echo "🚮 Model provider $PROVIDER is deleted"
