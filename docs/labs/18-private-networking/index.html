Lock down backend traffic with private networking

Create an AI Gateway with private routing through your virtual network, reach a Foundry backend over a private endpoint with its public access turned off, and learn which inbound options aren't available yet.

Advanced 45 min PortalCLIBicep Updated Oct 28, 2026
Source Edit

What you'll do

  • Explain which private networking options AI Gateway supports today, and why private routing is chosen at creation
  • Prepare a delegated integration subnet with an NSG that passes the gateway's subnet checks
  • Create a gateway with private routing through that subnet
  • Give Foundry a private endpoint and private DNS, turn off its public access, and prove the gateway still reaches it
  • Clean up in the right order, so the subnet and the Foundry resource are released

Before you start

  • 01Provision your AI Gateway
  • 12Call backends with managed identities

Tracks: Portal, Azure CLI, Bicep + azd

Your security team wants model traffic kept off the public internet wherever the platform allows it. With AI Gateway today, that's the hop from the gateway to your backends. In this lab you create a gateway with private routing, so its outbound calls leave through a subnet in your virtual network. Then you give the Foundry resource a private endpoint, turn off Foundry's public access, and prove that the gateway still reaches the model while the internet can't.

Important

Inbound private endpoints and disabling public network access aren't available for AI Gateway (Microsoft.ApiManagement/aigateways) yet. In the portal's create dialog, Public network access›Disabled is greyed out with "Unavailable until private frontend access is supported", the gateway has no private endpoint connections, and setting publicNetworkAccess to Disabled through Azure Resource Manager has no effect. Clients keep calling the gateway on its public endpoint, so protect it with runtime keys or Microsoft Entra ID (Issue and rotate runtime API keys, Go keyless with Microsoft Entra ID and RBAC) and an ipFilter policy (Set gateway-wide policy baselines).

#How it works

A gateway has two network directions. Inbound, clients call the gateway's frontend on https://<gateway>.<region>-01.ai.gateway.azure.com. Outbound, the gateway calls models, MCP servers, and APIs. With private routing, the gateway joins a dedicated, delegated subnet in your virtual network and sends its outbound calls through it, so it can reach backends on private IPs. When a backend's private DNS zones are linked to that virtual network, the gateway resolves the backend's usual host name to its private endpoint IP.

You choose private routing when you create the gateway, and you can't add, change, or remove it afterwards: "Virtual network integration for Azure AI Gateway can only be configured during creation." Most connectivity problems after that are DNS: the gateway must resolve each backend to its private IP.

#Create the network security group

Bash
# Create the network security group that the integration subnet uses
az network nsg create -g "$RG" -n "$NSG" -l "$LOCATION" -o none &&
  echo "🔒 NSG $NSG is ready"

# Allow outbound HTTPS (TCP 443) from the subnet to the Storage service tag, as the gateway's subnet checks require
az network nsg rule create -g "$RG" --nsg-name "$NSG" -n AllowStorageOutbound \
  --priority 100 --direction Outbound --access Allow --protocol Tcp \
  --source-address-prefixes VirtualNetwork \
  --destination-address-prefixes Storage --destination-port-ranges 443 -o none &&
  echo "🔒 NSG rule AllowStorageOutbound allows outbound TCP 443 to Storage"

# Allow outbound HTTPS (TCP 443) to the AzureKeyVault service tag, the other rule that the subnet checks require
az network nsg rule create -g "$RG" --nsg-name "$NSG" -n AllowKeyVaultOutbound \
  --priority 110 --direction Outbound --access Allow --protocol Tcp \
  --source-address-prefixes VirtualNetwork \
  --destination-address-prefixes AzureKeyVault --destination-port-ranges 443 -o none &&
  echo "🔒 NSG rule AllowKeyVaultOutbound allows outbound TCP 443 to AzureKeyVault"
2

#Create the virtual network and subnets

Bash
# Create the virtual network, with an address space that holds both subnets
az network vnet create -g "$RG" -n "$VNET" -l "$LOCATION" --address-prefixes 10.20.0.0/16 -o none &&
  echo "🔒 Virtual network $VNET is ready in $LOCATION"

# Create the integration subnet for the gateway alone: delegated to Microsoft.App/environments, with the NSG
az network vnet subnet create -g "$RG" --vnet-name "$VNET" -n "$INTEGRATION_SUBNET" \
  --address-prefixes 10.20.0.0/24 \
  --delegations Microsoft.App/environments --network-security-group "$NSG" -o none &&
  echo "🔒 Integration subnet $INTEGRATION_SUBNET (10.20.0.0/24) is ready"

# Create the subnet that holds the private endpoints to backends such as Foundry
az network vnet subnet create -g "$RG" --vnet-name "$VNET" -n "$PE_SUBNET" --address-prefixes 10.20.1.0/24 -o none &&
  echo "🔒 Private endpoint subnet $PE_SUBNET (10.20.1.0/24) is ready"

infra/private-network.bicep declares the NSG, the virtual network and its two subnets, and the gateway itself. It creates the gateway with the template from Provision your AI Gateway, gateway.bicep↗, used as a module, and passes the integration subnet in its backendSubnetId parameter, which becomes properties.backend.subnet.id. When you pass a Foundry resource ID in foundryAccountId, it also adds a private endpoint to Foundry with the account group ID, the three Foundry private DNS zones, their virtual network links, and a DNS zone group. You can also deploy it on its own to an existing resource group.

There's no inbound private endpoint and no publicNetworkAccess: 'Disabled' for the gateway in the template, because the aigateways resource type doesn't support them yet.

#Link the Foundry private DNS zones

Create each zone, link it to the virtual network, and add it to the endpoint's DNS zone group:

# For each Foundry private DNS zone: the first one creates the endpoint's DNS zone group, the others join it
first=true
for zone in privatelink.cognitiveservices.azure.com privatelink.openai.azure.com privatelink.services.ai.azure.com; do
  # Create the zone, and link it to the virtual network without auto-registration of records (-e false)
  az network private-dns zone create -g "$RG" -n "$zone" -o none &&
    echo "🔒 Private DNS zone $zone is ready"
  az network private-dns link vnet create -g "$RG" -z "$zone" -n "$VNET-link" -v "$VNET" -e false -o none &&
    echo "🔒 $zone is linked to $VNET"

  # Add the zone to the private endpoint's DNS zone group, so that Foundry's private IP gets an A record in it
  if $first; then action=create; first=false; else action=add; fi
  az network private-endpoint dns-zone-group "$action" -g "$RG" --endpoint-name "$FOUNDRY_PE" \
    -n default --private-dns-zone "$zone" --zone-name "${zone//./-}" -o none &&
    echo "🔒 $zone is in the DNS zone group of $FOUNDRY_PE"
done
# For each Foundry private DNS zone: the first one creates the endpoint's DNS zone group, the others join it
$zones = "privatelink.cognitiveservices.azure.com", "privatelink.openai.azure.com", "privatelink.services.ai.azure.com"
foreach ($zone in $zones) {
  # Create the zone, and link it to the virtual network without auto-registration of records (-e false)
  az network private-dns zone create -g $RG -n $zone -o none
  if ($?) { Write-Host "🔒 Private DNS zone $zone is ready" }
  az network private-dns link vnet create -g $RG -z $zone -n "$VNET-link" -v $VNET -e false -o none
  if ($?) { Write-Host "🔒 $zone is linked to $VNET" }

  # Add the zone to the private endpoint's DNS zone group, so that Foundry's private IP gets an A record in it
  $action = if ($zone -eq $zones[0]) { "create" } else { "add" }
  az network private-endpoint dns-zone-group $action -g $RG --endpoint-name $FOUNDRY_PE `
    -n default --private-dns-zone $zone --zone-name $zone.Replace('.', '-') -o none
  if ($?) { Write-Host "🔒 $zone is in the DNS zone group of $FOUNDRY_PE" }
}

#Go further

  • Filter who can call the gateway. While the frontend stays public, add a gateway-wide ipFilter policy (action: Allow with your egress cidrRanges) next to keys or Microsoft Entra ID. See Set gateway-wide policy baselines.
  • Hub-and-spoke networks. Keep backend private endpoints and their private DNS zones in a hub, peer the gateway's virtual network to it, and link the zones to the integrated virtual network. If you use your own DNS servers, forward the privatelink zones to Azure DNS. See Azure private endpoint DNS configuration↗.
  • Private MCP servers and APIs. Any backend with a private endpoint or a private IP that the integrated virtual network can reach works the same way, including the tool servers from Federate MCP tools behind one endpoint.
  • Data residency. Residency follows the whole request path, so account for where your backends, tools, logs, and clients live, not only the gateway region.
