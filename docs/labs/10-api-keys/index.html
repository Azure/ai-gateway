Issue and rotate runtime API keys

Give every app its own runtime API key, keep the value out of your code, rotate it without downtime with the primary and secondary values, revoke a leaked key, and see usage and cost per key in Monitoring.

Beginner 15 min PortalCLI Updated Oct 19, 2026
Source Edit

What you'll do

  • Create one runtime API key for each app and keep its value in a secret store, not in code
  • Rotate a key without downtime by moving clients between its primary and secondary values
  • Revoke a leaked key and confirm that the gateway rejects it with 401
  • Find usage and estimated cost for each key in Monitoring
  • Decide when to replace API keys with Microsoft Entra ID

Before you start

  • 01Provision your AI Gateway

Tracks: Portal, Azure CLI

Three callers now use your gateway: the app-dev web app, the support-bot agent, and a data scientist's notebook that was shared with the whole company, key included. In this lab you give each caller its own runtime API key, keep the values in a secret store, rotate the bot's key without taking it offline, and revoke the leaked notebook key. Because every key is a separate caller identity, you can also see who used what.

#Before you begin

  • Complete Provision your AI Gateway. You need the gateway, its resource group, and its runtime URL.
  • Recommended: complete Publish a Foundry model and make your first call, so you have a model alias to call. The checks in this lab call that alias. The gateway answers 404 for an alias it doesn't know before it checks the key, so without a real alias the checks can't tell accepted keys from rejected keys.
  • Permission to manage the gateway's keys, for example Contributor on its resource group. Reading a key value needs Microsoft.ApiManagement/aigateways/apiKeys/listSecrets/action, which Contributor includes.
  • Optional: an Azure Key Vault that uses Azure RBAC, where you have Key Vault Secrets Officer. You can create one below.
  • Optional, for usage and cost per key: monitoring configured in Monitor usage, cost, and traces.
  • For the CLI track and the Verify scripts: the Azure CLI↗ 2.75 or later, signed in with az login. The CLI track calls the Azure Resource Manager REST API with az rest, because the az aigateway extension doesn't manage the new aigateways resource type yet. The Bash scripts use curl; the PowerShell scripts need PowerShell 7 or later.

No Key Vault yet? Create one for this lab.

Key Vault names are globally unique, 3 to 24 characters. The vault uses Azure RBAC, and you get Key Vault Secrets Officer so you can write and read secrets. A new role assignment can take a few minutes to apply.

export KEY_VAULT="kv-aigw-$RANDOM"
az keyvault create -g "$RG" -n "$KEY_VAULT" --enable-rbac-authorization true -o none
az role assignment create --role "Key Vault Secrets Officer" \
  --assignee "$(az ad signed-in-user show --query id -o tsv)" \
  --scope "$(az keyvault show -n "$KEY_VAULT" --query id -o tsv)" -o none
$KEY_VAULT = "kv-aigw-$(Get-Random -Maximum 99999)"
az keyvault create -g $RG -n $KEY_VAULT --enable-rbac-authorization true -o none
az role assignment create --role "Key Vault Secrets Officer" `
  --assignee (az ad signed-in-user show --query id -o tsv) `
  --scope (az keyvault show -n $KEY_VAULT --query id -o tsv) -o none

#How it works

A runtime API key is a gateway resource with a name and two values, primary and secondary. Both values work at the same time, which is what makes rotation without downtime possible. Clients send either value in the api-key header. The model endpoint also accepts it as a bearer token, which is how OpenAI SDKs send their API key, but a request with both headers gets 400. The gateway validates the key before it applies policies or forwards the request, so a missing, wrong, rotated, or deleted value, or a suspended key, gets 401 Unauthorized and never reaches a model.

A key is gateway-scoped: it grants access to every published model and MCP server on the gateway. Each key is also a separate caller identity, which token limits, cost limits, and Monitoring use to tell callers apart. That's why every app, agent, or user should get its own key.

TaskPortal (Access›Keys)Azure CLI (az rest on $GW/apiKeys/<name>)
Create a keyCreate API keyPUT
Read a valueView keys (primary value)POST .../listSecrets (primary and secondary values)
RotateRotate key (primary value)POST .../regeneratePrimaryKey or .../regenerateSecondaryKey
Block temporarily—PATCH with state set to suspended, then back to active
RevokeDeleteDELETE

The gateway also has a built-in key named master. Don't hand it out; create named keys instead.

The script sends a tiny Chat Completions request and prints only the last four characters of the key. On GitHub, open check-key.sh↗ or check-key.ps1↗.

infra/check-key.shGitHub
#!/usr/bin/env bash
# Sends one small Chat Completions request through AI Gateway and reports whether the gateway accepted the
# runtime API key. Only the last four characters of the key are printed.
#
# Usage:
#   export AI_GATEWAY_URL="https://<gateway>.eastus2-01.ai.gateway.azure.com"
#   export AI_GATEWAY_MODEL="<model-alias>"
#   export AI_GATEWAY_API_KEY="..."                 # the key to test; never commit it
#   ./check-key.sh ["label"]                        # test AI_GATEWAY_API_KEY
#   AI_GATEWAY_API_KEY="$OLD_KEY" ./check-key.sh "old value"
#   ./check-key.sh --no-key                         # send the request without an api-key header
# Requires curl.
set -euo pipefail

: "${AI_GATEWAY_URL:?Set AI_GATEWAY_URL to https://<gateway>.eastus2-01.ai.gateway.azure.com}"
: "${AI_GATEWAY_MODEL:?Set AI_GATEWAY_MODEL to a callable model alias}"

URL="${AI_GATEWAY_URL%/}/default/models/openai/v1/chat/completions"
BODY=$(printf '{"model":"%s","messages":[{"role":"user","content":"ping"}]}' "$AI_GATEWAY_MODEL")

if [[ "${1:-}" == "--no-key" ]]; then
  LABEL="no key"
  HINT="-"
  RESPONSE=$(curl -sS -w '\n%{http_code}' "$URL" \
    -H "Content-Type: application/json" -d "$BODY" || true)
else
  : "${AI_GATEWAY_API_KEY:?Set AI_GATEWAY_API_KEY to the runtime key to test}"
  LABEL="${1:-current key}"
  HINT="...${AI_GATEWAY_API_KEY: -4}"
  # The header is read from stdin so the key doesn't appear in the process list.
  RESPONSE=$(printf 'api-key: %s\n' "$AI_GATEWAY_API_KEY" | curl -sS -w '\n%{http_code}' "$URL" \
    -H @- -H "Content-Type: application/json" -d "$BODY" || true)
fi
STATUS="${RESPONSE##*$'\n'}"

case "$STATUS" in
  2??) RESULT="accepted" ;;
  401) RESULT="rejected: the key is missing, invalid, rotated, suspended, or deleted" ;;
  404) if [[ "$RESPONSE" == *model_not_found* ]]; then
         RESULT="not checked: the gateway doesn't know the alias in AI_GATEWAY_MODEL"
       else
         RESULT="key accepted, but the call failed: check AI_GATEWAY_MODEL and the gateway's policies"
       fi ;;
  000|"") RESULT="no response: check AI_GATEWAY_URL and your network"; STATUS="---" ;;
  *)   RESULT="key accepted, but the call failed: check AI_GATEWAY_MODEL and the gateway's policies" ;;
esac

printf '%-14s %-8s HTTP %s  %s\n' "$LABEL" "$HINT" "$STATUS" "$RESULT"
Checkpoint

#Store the key outside your code

A runtime key opens every model and MCP server on the gateway, so treat it like a password:

  • Local development: set an environment variable for the session, as in this lab, and read it in code, for example os.environ["AI_GATEWAY_API_KEY"] in Python. If you keep it in a .env file, add the file to .gitignore.
  • Hosted apps: keep the value in Azure Key Vault. App Service and Azure Functions resolve Key Vault references↗ in app settings, and Azure Container Apps can reference Key Vault secrets↗.
  • Pipelines: use the secret store of your CI system, or read the value from Key Vault at run time.
  • Never put the value in source code, a committed .env file, build logs, notebooks, chat, or tickets.

If you set KEY_VAULT, store the app-dev and support-bot values there. The commands print only the secret IDs. Each secret is named <key>-api-key, which is the name the rotation script updates later.

for KEY in app-dev support-bot; do
  az keyvault secret set --vault-name "$KEY_VAULT" -n "$KEY-api-key" \
    --value "$(az rest --method post --url "$GW/apiKeys/$KEY/listSecrets?$API" --query primaryKey -o tsv)" \
    --tags aigateway-key="$KEY" key-type=primary --query id -o tsv
done
foreach ($key in "app-dev", "support-bot") {
  $value = az rest --method post --url "$GW/apiKeys/$key/listSecrets?$API" --query primaryKey -o tsv
  az keyvault secret set --vault-name $KEY_VAULT -n "$key-api-key" --value $value `
    --tags aigateway-key=$key key-type=primary --query id -o tsv
}
Remove-Variable value

An app, or you, then reads the value from the vault instead of from the gateway:

export AI_GATEWAY_API_KEY="$(az keyvault secret show --vault-name "$KEY_VAULT" -n app-dev-api-key --query value -o tsv)"
$env:AI_GATEWAY_API_KEY = az keyvault secret show --vault-name $KEY_VAULT -n app-dev-api-key --query value -o tsv
Note

The portal track can store the values the same way: run the commands above, or add the secrets to the vault in the Azure portal.

#Rotate a key without downtime

Rotate keys on a schedule, and whenever someone who had a value leaves the team. Regenerating a value invalidates that value only, and right away. The trick is to regenerate the value that no client is using.

  1. On the support-bot row, select … (More actions) › Rotate key.
  2. The Rotate "support-bot" key? dialog warns that the current value stops working immediately and that the new value is displayed once. Select Rotate.

Note

To rotate without downtime from the portal, replace the key instead: create support-bot-v2, move the client to it, and then delete support-bot. The new key is a new caller identity, so move any cost-limit overrides to it, and expect Monitoring to report it separately. The CLI track avoids both trade-offs with the secondary value.

#Save the current value

OLD_SUPPORT_BOT="$(az rest --method post --url "$GW/apiKeys/support-bot/listSecrets?$API" \

#Regenerate the unused secondary value

No client uses the secondary value, so regenerating it breaks nothing:

./infra/rotate-key.sh support-bot secondary
./infra/rotate-key.ps1 -ResourceGroup $RG -Gateway $GATEWAY -KeyName support-bot -KeyType secondary # -KeyVault $KEY_VAULT

The script calls the key's regenerateSecondaryKey action with az rest, reads the new value with listSecrets, and prints only its last four characters. If KEY_VAULT is set in Bash, or you pass -KeyVault in PowerShell, it also writes the new value to the support-bot-api-key secret. On GitHub, open rotate-key.sh↗ or rotate-key.ps1↗.

infra/rotate-key.shGitHub
#!/usr/bin/env bash
# Regenerates one value (primary or secondary) of an AI Gateway runtime API key, reads the new value, and
# optionally stores it in Azure Key Vault. Only the last four characters of the key are printed.
#
# Zero-downtime rotation for clients that use the primary value today:
#   ./rotate-key.sh support-bot secondary   # 1. issue a fresh secondary value that no client uses yet
#                                           # 2. move every client to the secondary value
#   ./rotate-key.sh support-bot primary     # 3. retire the old primary value
# Next time, swap the roles: regenerate primary first, move clients, then regenerate secondary.
#
# Usage:
#   export RG="<resource-group>" GATEWAY="<gateway>"
#   export KEY_VAULT="<key-vault-name>"     # optional: store the new value as secret <key-name>-api-key
#   ./rotate-key.sh <key-name> <primary|secondary>
# Requires the Azure CLI 2.75 or later. It calls the Azure Resource Manager REST API with az rest, because the
# az aigateway extension doesn't manage the Microsoft.ApiManagement/aigateways resource type yet.
set -euo pipefail

NAME="${1:?Usage: rotate-key.sh <key-name> <primary|secondary>}"
TYPE="${2:?Usage: rotate-key.sh <key-name> <primary|secondary>}"
case "$TYPE" in
  primary)   ACTION="regeneratePrimaryKey" ;;
  secondary) ACTION="regenerateSecondaryKey" ;;
  *) echo "error: the second argument must be primary or secondary" >&2; exit 2 ;;
esac
: "${RG:?Set RG to the gateway resource group}"
: "${GATEWAY:?Set GATEWAY to the gateway name}"

API="api-version=2025-09-01-preview"
GATEWAY_ID="$(az resource show -g "$RG" -n "$GATEWAY" --resource-type Microsoft.ApiManagement/aigateways \
  --query id -o tsv)"
KEY_URL="https://management.azure.com$GATEWAY_ID/apiKeys/$NAME"

az rest --method post --url "$KEY_URL/$ACTION?$API" -o none

VALUE="$(az rest --method post --url "$KEY_URL/listSecrets?$API" --query "${TYPE}Key" -o tsv)"
if [[ -z "$VALUE" ]]; then
  echo "error: couldn't read the new $TYPE value. You need the apiKeys/listSecrets/action permission." >&2
  exit 1
fi
echo "Regenerated the $TYPE value of '$NAME' (ends in ...${VALUE: -4})."

if [[ -n "${KEY_VAULT:-}" ]]; then
  SECRET="${NAME}-api-key"
  az keyvault secret set --vault-name "$KEY_VAULT" --name "$SECRET" --value "$VALUE" \
    --tags "aigateway-key=$NAME" "key-type=$TYPE" -o none
  echo "Stored it in Key Vault '$KEY_VAULT' as secret '$SECRET'."
else
  echo "Read it with: az rest --method post --url \"$KEY_URL/listSecrets?$API\" --query ${TYPE}Key -o tsv"
fi

#Move the client to the secondary value

Update the client's configuration to the new secondary value and restart it, or let it reload the Key Vault secret. Both values are valid now, so no request fails during the switch. The old primary value still works:

AI_GATEWAY_API_KEY="$OLD_SUPPORT_BOT" ./infra/check-key.sh "old primary"
./infra/check-key.ps1 -ApiKey $OLD_SUPPORT_BOT -Label "old primary"
4

#Regenerate the primary value

When every client uses the secondary value, regenerate the primary. This invalidates the old value, wherever it might have been copied:

./infra/rotate-key.sh support-bot primary
./infra/rotate-key.ps1 -ResourceGroup $RG -Gateway $GATEWAY -KeyName support-bot -KeyType primary # -KeyVault $KEY_VAULT

Next time, rotate in the other direction: regenerate the primary, move clients to it, then regenerate the secondary. With Key Vault, the secret always holds the newest value, so clients that reload it move along automatically.

Checkpoint

AI_GATEWAY_API_KEY="$OLD_SUPPORT_BOT" ./infra/check-key.sh "rotated value" (or ./infra/check-key.ps1 -ApiKey $OLD_SUPPORT_BOT -Label "rotated value") prints HTTP 401.

#Revoke a leaked key

When a key leaks, revoke it first and investigate afterward. Deleting a key invalidates both of its values immediately, and anyone who holds them gets 401. Pick one track.

#Save the leaked value

read -rsp "Leaked value: " LEAKED_KEY && echo

Select the check box on the old-notebook row, and then select Delete. The Delete "old-notebook" key? dialog warns that applications using the key will no longer authenticate to the gateway and that the action can't be undone. Select Delete.

1

#Save the leaked value and delete the key

LEAKED_KEY="$(az rest --method post --url "$GW/apiKeys/old-notebook/listSecrets?$API" \

az rest --method delete --url "$GW/apiKeys/old-notebook?$API"
$LEAKED_KEY = az rest --method post --url "$GW/apiKeys/old-notebook/listSecrets?$API" `

az rest --method delete --url "$GW/apiKeys/old-notebook?$API"
2

#Suspend a key instead

To block a key while you investigate, without deleting it, set its state to suspended. Calls with the key get 401 until you set it back to active. The Verify section expects support-bot to work, so set it back to active before you continue:

az rest --method patch --url "$GW/apiKeys/support-bot?$API" \
  --body '{"properties":{"state":"suspended"}}' --query properties.state -o tsv
# Later, to let the key work again:
az rest --method patch --url "$GW/apiKeys/support-bot?$API" \
  --body '{"properties":{"state":"active"}}' --query properties.state -o tsv
'{"properties":{"state":"suspended"}}' | Set-Content keystate.json
az rest --method patch --url "$GW/apiKeys/support-bot?$API" --body "@keystate.json" --query properties.state -o tsv
# Later, to let the key work again:
'{"properties":{"state":"active"}}' | Set-Content keystate.json
az rest --method patch --url "$GW/apiKeys/support-bot?$API" --body "@keystate.json" --query properties.state -o tsv
Remove-Item keystate.json

Each command prints the new state, suspended or active.

Then clean up after the leak: remove the value from the notebook and its history, and check Monitoring for calls made with the key.

Note

If the caller behind a leaked key must keep its identity, for example because a cost-limit override or Monitoring history is tied to it, regenerate both values instead of deleting the key. Run ./infra/rotate-key.sh <key> primary and then ./infra/rotate-key.sh <key> secondary (or the PowerShell script with -KeyType), and give the caller the new value.

#See usage and cost per key

Each key is a caller identity, so Monitoring can break usage down by key. This needs the monitoring setup from Monitor usage, cost, and traces and a few requests with each key.

  1. Select Monitoring›Models.
  2. Active caller identities counts the API keys and Microsoft Entra identities with observed activity.
  3. Model usage by caller identity compares caller identities by estimated model cost, tokens, and calls.
  4. Use the All caller identities filter to scope the page to one key, for example support-bot. Keys appear by name, marked API key.

#When to move to Microsoft Entra ID

API keys are the fastest way to start, but the docs don't recommend them for production.

Runtime API keyMicrosoft Entra ID with Azure RBAC
What the gateway seesOne named keyA user, agent, or workload identity in your tenant
What it can callEvery published model and MCP serverWhat its role grants: AI Gateway User (models and tools), AI Gateway Models User, or AI Gateway Tools User, at gateway, alias, or MCP server scope
Secret to protectThe key valueNone with a managed identity; tokens are short-lived
RotationYou rotate and redistribute valuesMicrosoft Entra ID issues new tokens
Good fitPrototypes, labs, and tools that only accept a keyProduction apps, agents, and per-user access

  • Prompt for the key in MCP clients. VS Code can ask for the key when it starts an MCP server instead of storing it in mcp.json. See Federate MCP tools behind one endpoint.
  • Get a rotation reminder. Set an expiry date on the Key Vault secret with az keyvault secret set-attributes --expires, and subscribe to the vault's SecretNearExpiry event.
  • Automate rotation. Run the rotation script from a scheduled pipeline that signs in with a workload identity, with a pause between the secondary and primary steps for clients to reload.
  • Limit each key. Give every key its own token allowance with Throttle tokens per caller with token limits.

#Clean up

Keep app-dev and support-bot: Enforce cost budgets with per-caller overrides gives them different budgets. Delete any other keys you created for testing, such as support-bot-v2, in Access›Keys (check box, then Delete), or with the CLI:

Bash
az rest --method delete --url "$GW/apiKeys/support-bot-v2?$API"

If you created a Key Vault only for this lab, delete it. Key Vault keeps deleted vaults for a retention period and reserves the name; purge it if you want to reuse the name right away:

Bash
az keyvault delete -n "$KEY_VAULT"
az keyvault purge -n "$KEY_VAULT"

Clear the key values from your shell with unset AI_GATEWAY_API_KEY OLD_SUPPORT_BOT LEAKED_KEY SUPPORT_BOT (Bash) or Remove-Variable OLD_SUPPORT_BOT, LEAKED_KEY, SUPPORT_BOT; Remove-Item Env:AI_GATEWAY_API_KEY (PowerShell). Delete the gateway only when you finish all labs, as described in Provision your AI Gateway.

#Troubleshooting

SymptomLikely causeFix
A new key gets 401The value has a space or line break, or an MCP client sends it in Authorization instead of api-keyCopy the value again and send it as api-key: <value>.
400 with Specify either an API key or an Authorization header, not bothThe client sends an api-key header and an Authorization headerSend one of them. With an OpenAI SDK, pass the key as the SDK's API key and remove the extra header.
401 right after Rotate key in the portalPortal rotation replaces the primary value immediatelyGive the client the value from API key rotated successfully. Next time, use the CLI secondary-value flow.
"The key was created, but its value couldn't be retrieved."You don't have Microsoft.ApiManagement/aigateways/apiKeys/listSecrets/actionUse Rotate key to get a new value, or ask someone with that permission, such as a Contributor, to read it.
check-key prints not checked with HTTP 404The gateway doesn't know the alias in AI_GATEWAY_MODEL, so it never checked the keySet AI_GATEWAY_MODEL to an alias from Models, for example the one from lab 02.
A key that worked gets 401, and nobody rotated itThe key is suspendedCheck state with the list command, and set it back to active if the suspension is over.
check-key prints key accepted, but the call failedThe key works, but AI_GATEWAY_MODEL isn't an alias you can call, or a policy blocked the requestSet AI_GATEWAY_MODEL to an alias from Models, for example the one from lab 02.
Forbidden from az keyvault secret set or secret showYou have no data-plane role on the vault, or the role assignment hasn't applied yetAssign Key Vault Secrets Officer on the vault and wait a few minutes.
Monitoring shows no caller identitiesMonitoring isn't configured, or the time range has no trafficComplete Monitor usage, cost, and traces, send requests with each key, and widen the time range.
