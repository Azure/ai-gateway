MCP & tools · Lab 04

Federate MCP tools behind one endpoint

Register a remote MCP server in AI Gateway, add a second backend under its own namespace, and connect curl, VS Code, and Python to one governed MCP endpoint.

Beginner 25 min PortalCLIBicepCode Updated Oct 19, 2026
Notebook Source Edit

What you'll do

  • Explain the four tool source types and how AI Gateway namespaces the tools of each backend
  • Register the public Microsoft Learn MCP server in the portal, with the Azure CLI, or with Bicep
  • Federate a second backend into the same MCP server and mark it optional
  • Connect curl, VS Code, and a Python MCP client to the governed endpoint with a runtime key

Before you start

  • 01Provision your AI Gateway

Tracks: Portal, Azure CLI, Bicep / azd, Code

Your agent teams want tools: documentation search, ticketing, internal APIs. If every agent connects to every tool server directly, you end up with credentials in many places and no single point of control. In this lab the platform team publishes one governed MCP endpoint on the gateway, starting with the public Microsoft Learn MCP server, so agents get tools through the same front door they already use for models.

#Before you begin

  • A runtime API key, for example app-first-call from lab 02. #How it works

An MCP server in AI Gateway is a federation point. You give it one or more backends, and the gateway publishes all their tools at one Streamable HTTP endpoint: https://<gateway>.eastus2-01.ai.gateway.azure.com/default/toolservers/<server-name>/mcp.

Backend typeWhat you provideWhat clients see
MCP server (remote)A URL that speaks SSE or Streamable HTTPThe server's tools
OpenAPI specA JSON or YAML OpenAPI document (upload, URL, or inline)Selected operations as tools. The operation summary or description becomes the tool description.
Built-in connectorA managed connection to a SaaS app, such as Microsoft 365, SharePoint, GitHub, or SalesforceThe connector's operations as tools
Foundry ToolboxA Microsoft Foundry Toolbox sourceThe toolbox's tools

Each backend can have a namespace. The gateway prefixes that backend's tools with it, as in learn_microsoft_docs_search, so two backends can expose tools with the same name without conflict.

The gateway authenticates clients. In this lab they send a runtime key in the api-key header. It authenticates to each backend separately, with None, API key (a header name and value), OAuth 2.0, or Managed identity. Backend credentials are stored securely, are never exposed to clients, and appear under Connections.

Note

Registering a backend doesn't mean that AI Gateway translates every backend protocol into MCP. Pick the backend type that matches what the backend actually serves.

#Create the registration

MCP servers are toolServers child resources of the gateway's default workspace.

az rest --method put --url "$WS/toolServers/learn?$API" --body '{
  "properties": {
    "type": "mcp",
    "displayName": "Microsoft Learn",
    "description": "Search and fetch official Microsoft documentation and code samples.",
    "endpoints": [{"kind": "mcp", "namespace": "learn", "required": true,
                   "mcp": {"transport": "streamableHttp", "url": "https://learn.microsoft.com/api/mcp"}}]
  }}' \
  --query "{name:name,mcpEndpoint:properties.gatewayEndpoints[0].url}"
@{ properties = @{
    type        = 'mcp'
    displayName = 'Microsoft Learn'
    description = 'Search and fetch official Microsoft documentation and code samples.'
    endpoints   = @(@{ kind = 'mcp'; namespace = 'learn'; required = $true
                       mcp  = @{ transport = 'streamableHttp'; url = 'https://learn.microsoft.com/api/mcp' } })
  } } | ConvertTo-Json -Depth 10 -Compress | Set-Content -Path body.json
az rest --method put --url "$WS/toolServers/learn?$API" --body '@body.json' `
  --query "{name:name,mcpEndpoint:properties.gatewayEndpoints[0].url}"
Remove-Item body.json

The last segment of the URL, learn, is the MCP server name. A PUT replaces an existing registration with the same name, including its backends and policies, so use PATCH to change a registration that already exists, as in the next section.

#Review the template

The template references your existing gateway and its default workspace, then declares one toolServers resource. The optional secondNamespace parameter is used in the next section.

infra/main.bicepGitHub
// Registers the public Microsoft Learn MCP server as a federated MCP server in an existing AI Gateway.
// Clients call one governed endpoint, https://<gateway>.eastus2-01.ai.gateway.azure.com/default/toolservers/<serverName>/mcp,
// and the gateway publishes each backend's tools with a namespace prefix (<namespace>_<tool>).
// Set secondNamespace to add the same public server as a second, optional backend and see namespacing at work.

@description('Name of the existing AI Gateway (Microsoft.ApiManagement/aigateways).')
param gatewayName string

@description('MCP server name. It becomes part of the endpoint URL and cannot be changed after creation.')
param serverName string = 'learn'

@description('Display name shown in the portal catalog and details page.')
param displayName string = 'Microsoft Learn'

@description('Description that helps people and agents understand what the tools do.')
param serverDescription string = 'Search and fetch official Microsoft documentation and code samples.'

@description('Namespace for the first backend. Its tools are published as <namespace>_<tool>.')
param namespace string = 'learn'

@description('URL of the first backend MCP server (Streamable HTTP).')
param mcpUrl string = 'https://learn.microsoft.com/api/mcp'

@description('Optional namespace for a second backend. Leave empty to register one backend only.')
param secondNamespace string = ''

@description('URL of the optional second backend MCP server (Streamable HTTP).')
param secondMcpUrl string = 'https://learn.microsoft.com/api/mcp'

var primaryEndpoint = {
  namespace: namespace
  kind: 'mcp'
  mcp: {
    url: mcpUrl
    transport: 'streamableHttp'
  }
  required: true
}

var secondEndpoint = {
  namespace: secondNamespace
  kind: 'mcp'
  mcp: {
    url: secondMcpUrl
    transport: 'streamableHttp'
  }
  required: false
}

resource gateway 'Microsoft.ApiManagement/aigateways@2025-09-01-preview' existing = {
  name: gatewayName
}

resource workspace 'Microsoft.ApiManagement/aigateways/workspaces@2025-09-01-preview' existing = {
  parent: gateway
  name: 'default'
}

resource toolServer 'Microsoft.ApiManagement/aigateways/workspaces/toolServers@2025-09-01-preview' = {
  parent: workspace
  name: serverName
  properties: {
    displayName: displayName
    description: serverDescription
    type: 'mcp'
    failureMode: 'failClosed'
    endpoints: empty(secondNamespace) ? [ primaryEndpoint ] : [ primaryEndpoint, secondEndpoint ]
  }
}

output toolServerId string = toolServer.id
output mcpEndpoint string = 'https://${gateway.properties.frontend.defaultHostname}/default/toolservers/${serverName}/mcp'

#Federate a second backend

Federation pays off when one endpoint combines several backends. To see it without extra credentials, add the same public Learn server again under a second namespace, docs. Both backends expose a tool called microsoft_docs_search, and the namespaces keep them apart. Mark the new backend as not required: if an optional backend is unavailable, the gateway skips it instead of failing the whole MCP server.

#Add the backend

#Add the source

A PATCH of properties.endpoints replaces the whole list of backends, so read the list, append the new backend, and send the result back. Other settings, such as the description and policies, stay as they are.

az rest --url "$WS/toolServers/learn?$API" --query properties.endpoints -o json \
  | jq -c '{properties: {endpoints: (map(select(.namespace != "docs")) + [{kind: "mcp", namespace: "docs",
      required: false, mcp: {transport: "streamableHttp", url: "https://learn.microsoft.com/api/mcp"}}])}}' > endpoints.json
az rest --method patch --url "$WS/toolServers/learn?$API" --body @endpoints.json \
  --query "properties.endpoints[].{namespace:namespace,required:required,url:mcp.url}" -o table
rm endpoints.json
$endpoints = @(az rest --url "$WS/toolServers/learn?$API" --query properties.endpoints -o json | ConvertFrom-Json |
  Where-Object namespace -ne 'docs')
$endpoints += @{ kind = 'mcp'; namespace = 'docs'; required = $false
                 mcp  = @{ transport = 'streamableHttp'; url = 'https://learn.microsoft.com/api/mcp' } }
@{ properties = @{ endpoints = $endpoints } } | ConvertTo-Json -Depth 10 -Compress | Set-Content -Path endpoints.json
az rest --method patch --url "$WS/toolServers/learn?$API" --body '@endpoints.json' `
  --query "properties.endpoints[].{namespace:namespace,required:required,url:mcp.url}" -o table
Remove-Item endpoints.json

The filter drops an existing docs backend first, so running the command twice doesn't add it twice. A GET doesn't return backend credentials. If a backend uses an API key, include its credential again in the body.

#Call the tools from Python

This client uses the official MCP Python SDK↗ and sends the runtime key in the api-key header.

infra/list_tools.pyGitHub
"""List, and optionally call, the tools that an AI Gateway MCP server publishes.

Usage:
    export AI_GATEWAY_URL="https://<gateway>.eastus2-01.ai.gateway.azure.com"
    export AI_GATEWAY_API_KEY="..."      # never commit this value
    python list_tools.py [server-name] [tool-name] [query]

Examples:
    python list_tools.py learn
    python list_tools.py learn learn_microsoft_docs_search "What is AI Gateway?"

Set AI_GATEWAY_MCP_ENDPOINT to use a full MCP endpoint URL instead of building it from AI_GATEWAY_URL.
"""

import asyncio
import os
import sys

import httpx
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client
from mcp.shared.exceptions import McpError


def endpoint(server: str) -> str:
    if os.environ.get("AI_GATEWAY_MCP_ENDPOINT"):
        return os.environ["AI_GATEWAY_MCP_ENDPOINT"]
    base = os.environ.get("AI_GATEWAY_URL")
    if not base:
        sys.exit("Set AI_GATEWAY_URL to https://<gateway>.eastus2-01.ai.gateway.azure.com")
    return f"{base.rstrip('/')}/default/toolservers/{server}/mcp"


async def main() -> None:
    server = sys.argv[1] if len(sys.argv) > 1 else "learn"
    tool = sys.argv[2] if len(sys.argv) > 2 else None
    query = sys.argv[3] if len(sys.argv) > 3 else "What is the AI gateway in Azure API Management?"
    api_key = os.environ.get("AI_GATEWAY_API_KEY")
    if not api_key:
        sys.exit("Set AI_GATEWAY_API_KEY to a runtime key from Access > Keys")

    url = endpoint(server)
    print(f"MCP endpoint: {url}")

    # The gateway authenticates the client with the runtime key in the api-key header.
    async with httpx.AsyncClient(headers={"api-key": api_key}, timeout=60) as http_client:
        async with streamable_http_client(url, http_client=http_client) as (read, write, _):
            async with ClientSession(read, write) as session:
                init = await session.initialize()
                print(f"Server: {init.serverInfo.name}  protocol: {init.protocolVersion}\n")

                result = await session.list_tools()
                for t in result.tools:
                    description = " ".join((t.description or "").split())[:70]
                    print(f"{t.name:<45} {description}")
                print(f"\n{len(result.tools)} tools published")

                if tool:
                    print(f"\nCalling {tool} with query: {query}")
                    try:
                        call = await session.call_tool(tool, {"query": query})
                    except McpError as error:
                        print(f"The tool call failed: {error}")
                        return
                    text = "\n".join(c.text for c in call.content if c.type == "text")
                    if call.isError:
                        print(f"The tool call failed: {text}")
                        return
                    print(text[:600] + "\n...")


if __name__ == "__main__":
    asyncio.run(main())

#Send a raw JSON-RPC request

The docs show the smallest possible request: a single JSON-RPC tools/list call. Streamable HTTP clients should also accept both JSON and SSE responses.

Bash
curl -sS "${AI_GATEWAY_URL%/}/default/toolservers/learn/mcp" \
  -H "api-key: $AI_GATEWAY_API_KEY" -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

The answer is JSON or an SSE data: line with a result.tools array. If the server answers with a JSON-RPC error instead, it requires the full handshake. Use the script, which runs it for you.

4

#Prove that the gateway checks the caller

Send the same request without the key:

Bash
curl -sS -o /dev/null -w "HTTP %{http_code}\n" "${AI_GATEWAY_URL%/}/default/toolservers/learn/mcp" \
  -H "Content-Type: application/json" -H "Accept: application/json, text/event-stream" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

The gateway rejects the request, typically with 401, and no backend is called. Microsoft Learn is public, but your MCP endpoint isn't.

Checkpoint

The script lists namespaced tools from both backends, a tool call returns Microsoft Learn content, and a request without a key is rejected.

#Go further

  • Control the catalog. Publish only approved tools, block risky ones, and rate-limit the server in Control which tools agents can call.
  • Screen tool traffic. Content safety also screens tool inputs and responses on MCP servers. See Screen prompts and responses with content safety.
  • Go keyless. Grant callers the AI Gateway User role and send a Microsoft Entra token instead of a runtime key. See Go keyless with Microsoft Entra ID and RBAC.
  • Watch tool traffic. When Application Insights is configured, tool executions appear in Monitoring›Tools. See Monitor usage, cost, and traces.
  • Onboard GitHub. Add the GitHub MCP server, https://api.githubcopilot.com/mcp/, as an MCP server backend with API key authentication: Header name Authorization and Key value Bearer <your-github-token>. The gateway stores the token, and clients never see it.
  • Give tools to an agent. Point an agent framework at the endpoint in Connect agent frameworks to models and tools.

#Troubleshooting

SymptomLikely causeFix
401 from the MCP endpointThe key is missing, revoked, or sent in the wrong headerSend a runtime key from Access›Keys in the api-key header.
404 from the MCP endpointWrong server name in the URL, or the server is still provisioningList the servers with az rest --url "$WS/toolServers?$API" --query "value[].name" and use the exact name in /default/toolservers/<server-name>/mcp.
406 or an error about the Accept headerThe client doesn't accept both JSON and SSESend Accept: application/json, text/event-stream, or use an MCP SDK.
