# Authoring Azure AI Gateway labs

Every lab is a folder under `labs/`. Its `README.md` is the **single source of truth** for two views: a rich page
on the **labs site** (`docs/`, published with GitHub Pages) and a self-contained lab you can follow **on GitHub**.
`npm run build` in `labs/` generates the site and refreshes the GitHub navigation in the READMEs (see
[GitHub view](#github-view)). Don't edit files in `docs/` by hand.

```text
labs/
├── catalog.json                 # categories, learning paths, use-case map
├── quickstart/                  # the 5-minute quick start: the only lab without a number
├── SETUP.md                     # the Setup guide: common tasks that every lab links to
├── TROUBLESHOOTING.md           # the Troubleshooting page: errors, likely causes, and fixes for every lab
├── RELEASE-NOTES.md             # labs release notes, aligned with the product releases
├── assets/                      # shared images: screens/, diagrams/, providers/
├── 06-token-limits/
│   ├── README.md                # the lab (metadata + Markdown + generated GitHub chrome)
│   ├── 06-token-limits.ipynb    # optional: the lab as a Jupyter notebook
│   └── infra/                   # optional: Bicep, scripts, sample code referenced by the lab
├── skills/azure-ai-gateway-labs/SKILL.md   # agent skill for coding agents (catalog generated by npm run sync)
├── tools/product-releases.mjs   # lists product releases and flags the ones RELEASE-NOTES.md doesn't cover
└── site/                        # site engine (templates, CSS, JS) – not lab content
```

## Metadata

Start the README with YAML metadata wrapped in an HTML comment, so GitHub hides it. The first line must be exactly
`<!--`. Classic `---` front matter also works; `npm run sync` converts it.

```yaml
<!--
title: Throttle tokens per caller with token limits     # sentence case, outcome-oriented
summary: One or two sentences shown on catalog cards and in search.
category: governance            # foundations | models | tools | governance | security | observability | agents | production
level: Beginner                 # Beginner | Intermediate | Advanced
duration: 25                    # minutes, realistic for a first-timer
tracks: [portal, cli, rest, iac] # portal | cli | iac | code | rest – only tracks the lab really offers
order: 6                        # catalog order (matches folder number; the quick start uses -1)
status: new                     # optional: new | preview | emerging
illustration: diagrams/token-limits.svg   # optional, relative to labs/assets/
tags: [tokenLimit, 429, TPM]
objectives:                     # 3–5 measurable outcomes ("You will …" is implied)
  - Explain how token limits are counted per caller identity
  - Add a token limit policy in the portal, with the CLI, or with REST
  - Trigger and interpret a 429 response with Retry-After
prereqs:                        # lab folder names, rendered as links
  - 02-first-model-call
-->
```

### The quick start

`quickstart/` is the only lab without a number. It sets `order: -1`, so it comes before lab 00 everywhere, and the
site shows a ⚡ instead of a number and "Quick start" instead of "Lab NN". The home page's hero and its **Start here**
band link to it. Keep it to five minutes, with no notebook: a portal track, an Azure CLI track that runs in
Cloud Shell, and a Bicep + azd track. Like every lab, its **Before you begin** starts with the **One-time setup**
card, and the later labs reuse that setup. The Bicep + azd track moves into `quickstart/` in the clone and deploys
its `azure.yaml` and `infra/` (see [azd templates](#azd-templates)). It uses lab 02's names (`foundry-models`, `gpt-6-luna`, `app-first-call`), so
labs 03 onward work on its gateway. Each track ends with the first call and then its own **Clean up** step, so the lab
has no separate call, verify, or clean up section. Teach the details in labs 00 to 02 instead.

### The Setup guide

[`SETUP.md`](SETUP.md) holds the tasks that every lab shares, and the site renders it at `/setup/` and in a panel
that slides in like **Your values**. The lab's right rail and its header open the panel, and so does any link to a
Setup guide section. Readers mark each task **Done** in the panel or on the page, and the browser remembers the marks
(`localStorage` key `aigw-setup`). Its sections are:

- Check your subscription and permissions
- Choose where to run commands
- Sign in to Azure
- Install the aigateway extension
- Register the resource providers
- Find the available regions
- Clone the labs repo
- Deploy a lab with azd, and Delete what azd created

The task table at the top of `SETUP.md` lists the tasks and when each one is needed, and `site/setup.mjs` maps a
short key to each task's section:

| Key | Task |
|---|---|
| `permissions` | Check your subscription and permissions |
| `tools` | Choose where to run commands: Cloud Shell, or the Azure CLI, azd, Git, `jq`, `curl`, and PowerShell 7 |
| `sign-in` | Sign in to Azure |
| `extension` | Install the aigateway extension |
| `providers` | Register the resource providers |
| `regions` | Find the available regions |
| `clone` | Clone the labs repo |

List the tasks that a lab needs with a directive on its own line, right after `## Before you begin`:

```markdown
## Before you begin

<!-- setup: tools sign-in extension clone -->
```

The site renders a **One-time setup** card with a checkbox per task. Tasks the reader marked done drop off the card,
and the card shrinks to one line when they're all done. On GitHub, `npm run sync` writes a `setup` region with a
link to each task. Don't repeat those tasks as bullets, links, or steps in the lab: no tool lists, no sign-in, and
no **Clone the lab** step. Keep only what's specific to the lab, such as Python for a Code track, a sign-in as a user,
or its extra resource providers. The build fails on an unknown key, and checks every link to a Setup guide anchor.

If a step must do a setup task inline, put `<!-- setup-done: keys -->` on its own line, right after its `###`
heading: checking the step's **Done** box then marks those tasks done in the Setup guide too. No lab needs it today.

### The Troubleshooting page

[`TROUBLESHOOTING.md`](TROUBLESHOOTING.md) holds the errors that readers might hit, with their likely causes and
fixes, and the site renders it at `/troubleshooting/` with a filter. It starts with **Setup and deployment**, then has
one section per lab: `## Quick start`, then `## Lab NN: <short title>`, with the lab's short title from
`catalog.json` and "and" instead of "&". Keep `·` and `&` out of these headings, because the site and GitHub turn
them into different anchors. Each section starts with a link to the lab, then a table whose first column, **Step**,
names the steps where readers see each error:

```markdown
## Lab 06: Token limits

Lab 06: [Throttle tokens per caller with token limits](06-token-limits/README.md)

| Step | Symptom | Likely cause | Fix |
|---|---|---|---|
| Run the burst | Every request returns `200`, never `429` | The limit is on a different model or alias than the one you call | … |
| Publish the model (Azure CLI)<br>Deploy with azd up | … | … | … |
```

Put the error code or the exact message in **Symptom**, so readers can filter for it. Write links relative to
`labs/`, for example `06-token-limits/README.md#verify` or `SETUP.md#sign-in-to-azure`.

In **Step**, write the step titles exactly as their `###` headings, separated by `<br>`. Name the step where the
reader sees the error, which isn't always the step that causes it. A title matches the steps with that title in every
track; to match only some tracks, add their tab labels in parentheses, such as `Make your first call (Azure CLI,
Bicep + azd)`. Write `Any step` for an error that no step owns. **Setup and deployment** has no Step column.

Labs don't have a `## Troubleshooting` section. On the site, each step with errors gets a **Troubleshoot** button
next to **Done**, with the number of errors. It opens the Troubleshooting panel with only that step's errors, and
**Show all errors** shows the rest of the lab's section. The build moves the Step column under each symptom as links
to the steps. The lab's right rail links to the lab's section, every link to the page opens it in the panel except
on the page itself, and the GitHub footer of each lab README links to its section. The build warns when a lab still
has a `## Troubleshooting` section, when no section starts with a link to a lab, when a lab's table has no Step
column, and when a step title or track label doesn't match the lab.

### azd templates

A lab folder with an `azure.yaml` at its root (not in `infra/`) is an azd template. `azd init` can't start from a
folder of a repo, so the reader clones the repo (the `repo` in `catalog.json`) once, moves into the lab folder, and
runs azd there. The clone also gets the other labs. The `clone` task of the lab's `<!-- setup: -->` directive
covers the clone, so the track has no clone step. Its **Deploy with azd up** step starts by moving into the lab
folder:

````markdown
```bash title="Bash"
# Move into the lab's folder, which holds the azd project
cd ~/ai-gateway/labs/<lab> &&
  echo "📂 Lab folder: $(pwd)"
```
````

The clone gets the default branch, which must be the `branch` in `catalog.json`. The build warns when a lab has a
template but neither clones the repo, lists the `clone` setup task, nor links to the Setup guide's clone section, when
no code block moves into the lab folder, or when a clone block uses another branch. The clone works once the lab is on
`main`. Keep secrets out of the template's outputs, because azd saves them in `.azure/<environment>/.env`.

Every lab's **Bicep + azd** track is a self-contained azd template, so it never needs a gateway from an earlier
lab. Follow [lab 06](06-token-limits/) and the quick start:

```text
06-token-limits/
├── azure.yaml                   # name: aigw-lab06, infra: { provider: bicep, path: infra }
└── infra/
    ├── main.bicep               # targetScope = 'subscription': rg-<env>, the base module, then the lab's modules
    ├── main.parameters.json     # environmentName, location, and the lab's knobs as "${VAR=default}"
    └── limited-alias.bicep      # the lab's own resource-group-scoped module, named after what it declares
```

- `main.bicep` takes `environmentName` and `location` (no `@allowed` list, since the regions change), names
  resources with `take(uniqueString(subscription().id, environmentName, location), 6)`, tags them with
  `azd-env-name`, and creates the resource group `rg-<environment>`.
- Reuse a base module rather than copying resources: [`quickstart/infra/resources.bicep`](quickstart/infra/resources.bicep)
  for a gateway with the `foundry-models` provider, the `gpt-6-luna` alias, and the `app-first-call` key, or
  [lab 01's `gateway.bicep`](01-provision-gateway/infra/gateway.bicep) for a gateway alone. Keep the parameters of
  shared modules backward compatible, because other labs and the notebooks call them.
- Name outputs the same way in every lab: `AZURE_RESOURCE_GROUP`, `AI_GATEWAY_NAME`, `AI_GATEWAY_ID`,
  `AI_GATEWAY_URL`, `AI_GATEWAY_PROVIDER`, `AI_GATEWAY_BACKEND_MODEL`, `AI_GATEWAY_MODEL`, and
  `FOUNDRY_ACCOUNT_NAME`, plus the lab's own in `UPPER_SNAKE_CASE`. The track reads them with
  `azd env get-value` into the variables that the lab's **Verify** section uses, and reads the key with
  `az aigateway api-key list-secrets`.
- To change a setting, the reader runs `azd env set <VAR> <value>` and `azd provision`. azd converts the value to
  the parameter's type, including integers and JSON arrays such as `'["ipAddress"]'`. Feed secrets to `@secure()`
  parameters the same way, and the signed-in user's object ID with `${AZURE_PRINCIPAL_ID}`.
- The track's sections are **Review the templates** (with `<!-- include: -->`), **Deploy with azd up** (`cd` into the
  lab folder, `azd env new aigw-labNN --location eastus2 --subscription …`, then `azd up`), and **Read the outputs and
  the key**. Its **Clean up** section runs `azd down --purge --force`, which deletes the resource group and purges the
  Foundry account. Add a `[!TIP]` to **Before you begin** saying the track needs no earlier lab.
- The track's label is **Bicep + azd**. The site shows the label of the lab's first `iac` marker instead when a lab
  uses another one, such as **Policy as code** in lab 09 or **Bicep** in lab 21.

## GitHub view

`npm run sync` (also run by `npm run build`) reads the metadata and `catalog.json` and adds GitHub-only chrome to
each README, so the lab reads well on github.com:

| Generated | What readers see on GitHub |
|---|---|
| `nav` region above the H1 | Breadcrumb back to the lab catalog and the lab's category |
| `intro` region below the H1 | Summary, a time, level, tracks, and prerequisites table, the objectives, links to the interactive version, the video walkthrough, the notebook, and `infra/`, and an **On this page** list of the H2 sections |
| `<details>` lines around tracks | Each track becomes a collapsible section; the first one is open |
| `<details>` lines around titled code blocks | Bash/PowerShell (and other) tab groups become collapsible sections |
| `setup` region after `<!-- setup: … -->` | **One-time setup** with a link to each Setup guide task the lab needs |
| `include` region after `<!-- include: … -->` | The included file's code, with a link to the file; files over 28 lines are collapsed |
| `widget` region after `<!-- widget: … -->` | A pointer to the interactive simulator on the site |
| `video` region after `<!-- video: … -->` | A poster image that opens the video on the site, plus links to the MP4 and captions |
| `footer` region at the end | Previous lab, all labs, next lab, and the learning paths that contain the lab |

It also refreshes the `badges`, `paths`, `catalog`, and `notebooks` regions of [`labs/README.md`](README.md), and
the `catalog`, `paths`, and `usecases` regions of the
[`azure-ai-gateway-labs` agent skill](skills/azure-ai-gateway-labs/SKILL.md), which the build publishes to
`docs/skills/`. Edit the rest of the skill by hand when you change lab conventions or runtime facts.

Generated regions sit between `<!-- gh:begin … -->` and `<!-- gh:end -->`; generated single lines end with
`<!-- gh -->`. Don't edit them: sync rewrites them from the metadata, and the site build strips them before
rendering, so the site never shows them. Write everything else as usual. After you change a lab, its metadata,
an included file, or `catalog.json`, run `npm run sync` and commit the README changes. `npm run check` fails if a
README is out of sync.

## Lab anatomy

Use these H2 sections in this order. Keep the H1 identical to `title`.

1. `# Title` then a 2–4 sentence **scenario** paragraph: who has the problem and why the gateway solves it.
   Follow with the illustration (`![…](../assets/diagrams/x.svg)`) and, when useful, an interactive widget.
2. `## Before you begin` – a `<!-- setup: … -->` directive for the [Setup guide](#the-setup-guide) tasks, then
   what's specific to the lab: its tools, permissions, and the outputs of prerequisite labs. Link prerequisites.
3. `## How it works` – the concept in under 200 words, a table of key values, and a widget or diagram.
4. One or more task sections (for example `## Add a token limit`). Put multi-track instructions in
   track tabs. Each `###` heading inside a track becomes a numbered step with a **Done** checkbox.
5. `## Verify` – prove it works. End major tasks with a **Checkpoint** callout.
6. `## Clean up` – always present. Say what is safe to delete and what is shared with other labs.
7. `## Next steps` – 2–4 links to related labs and docs.

Put the lab's errors on the [Troubleshooting page](#the-troubleshooting-page), mapped to their steps, not in the lab.

## Markdown conventions

All conventions are HTML comments or standard GitHub Markdown, so the README still reads cleanly on GitHub.

### Track tabs

````markdown
<!-- track: portal | Portal -->
### Open the policy wizard
In the [AI Gateway portal](https://ai.gateway.azure.com), select **Policies** › **Add policy**.

<!-- track: cli | Azure CLI -->
### Set the policy
```bash
az aigateway model policy set-token-limit -g "$RG" --gateway-name "$GATEWAY" --provider-name "$PROVIDER" \
  -n "$MODEL" --token-limit 1000 --token-period minute
```

<!-- /tracks -->
````

- Consecutive `<!-- track: id | Label -->` markers form one tab group; `<!-- /tracks -->` closes it.
- Track ids: `portal`, `cli`, `iac`, `code`, `rest`. The reader's choice is remembered across labs.
- Each `###` inside a track is a step. Keep steps small: one screen or one command block.
- Use `<!-- steps -->` … `<!-- /steps -->` to number `###` steps outside track tabs.

### Click paths

Write UI navigation as bold items separated by `›`: `**Policies** › **Add policy** › **Token rate limit**`.
These render as breadcrumb chips. Use the exact portal labels listed in the facts sheet.

### Placeholders

Use these placeholders in commands and URLs. On the site, readers can enter their values once and every
code block updates (values are stored in the browser; secrets are never stored):

`<subscription-id>` `<resource-group>` `<gateway>` `<location>` `<model-name>` `<provider-name>`
`<foundry-account-name>` `<tenant-id>`

For secrets, use shell variables (`$AI_GATEWAY_API_KEY`) and show how to set them, never inline values.

### Code blocks

- Always set the language. Add `title="…"` to label a block.
- Two or more **adjacent** titled blocks become language tabs (for example `title="Bash"` and
  `title="PowerShell"`, or `title="Python"` / `title="TypeScript"` / `title="C#"`). The choice is synced across the page.
- Include files from the lab folder: `<!-- include: infra/main.bicep -->` (optional language: `<!-- include: infra/x.sh bash -->`).
  The site shows the file with a GitHub link and collapses long files. On GitHub, add a normal link next to it.

#### CLI comments and status lines

Every command in a Bash or PowerShell block has a `#` comment above it that says what it does and why, and prints a
short status line with an emoji, so that readers see at a glance what happened. The
[quick start](quickstart/README.md) is the model.

- **Comments:** one line, two at most, starting with a verb, in sentence case with no trailing period. Explain
  non-obvious flags and values, such as `--no-wait`, a capacity, or a role GUID. Separate the groups with blank
  lines, and keep emoji out of comments.
- **Status lines after actions:** in Bash, end the command with `&&` and indent
  `echo "📦 Resource group $RG is ready"` on the next line. In PowerShell, add `if ($?) { Write-Host "…" }` on the
  next line. Either way, the line prints only when the command succeeds, so a missing line means a failure.
- **Values:** after a read into a variable, print it with a label, such as `echo "🌐 Runtime URL: $AI_GATEWAY_URL"`.
  When the command's own output is the point (a table, a JSON body, headers, a stream), print a labeled header
  line before it instead.
- **Model replies:** format them with `jq -r 'if .choices then "🤖 \(…)" else "🚨 \(.error.message // .)" end'`
  in Bash and `if ($?) { Write-Host "🤖 $($reply.choices[0].message.content)" }` in PowerShell. Label a failure
  that a policy causes on purpose, such as a 429, with 🚦.
- **Secrets:** never print a key or a token. Print its length:
  `echo "🔑 Key: in AI_GATEWAY_API_KEY (${#AI_GATEWAY_API_KEY} characters, not shown)"`.
- **Blocks for either shell** (`title="Bash or PowerShell"`, untitled `bash` blocks with only `az`, `azd`, `cd`,
  or `git` commands, and SDK installs): a comment, the command ending with `&&`, and a literal
  `echo "<emoji> …"` with no variables on the next line. `&&` works in Bash and in PowerShell 7, which the labs
  need.
- **Pitfalls:** no `!` in Bash echo strings, and write `"${VAR}:"` instead of `"$VAR:"` in PowerShell strings.
- **Paste-safe Bash:** readers paste blocks into macOS zsh, often with oh-my-zsh. When a paste arrives line by line,
  its `url-quote-magic` backslash-escapes `}`, `]`, `)`, `*`, `?`, and the other glob characters that follow a URL
  on a line that continues an open quote or heredoc, so a JSON value or a jq filter breaks. Keep such a value on one
  line, or put a comma or a space right after the URL. Prefer the Azure CLI shorthand syntax, such as
  `--foundry "{endpoint:'$FOUNDRY_ENDPOINT',resourceIds:[$FOUNDRY_ID]}"`, over JSON that jq builds, because the
  same value works in Bash and PowerShell.
- Use the same emoji for the same kind of thing, and only the ones in this table. zsh 5.9, the macOS default, draws
  newer emoji such as 🧠 and 🪪 as `<0001f9e0>`, and miscounts the width of emoji with a variation selector, such as
  🛡️ and ⚠️, so a pasted block shows garbled. Every emoji here is one code point that zsh draws two cells wide:

  | Emoji | Use | Emoji | Use |
  |---|---|---|---|
  | 📦 | Resource group, extension, SDK, or resource provider | 🔑 | API key, never its value |
  | 📝 | Variables, settings, or an azd environment | 👤 | Identity, sign-in, or token |
  | 🏭 | Foundry account | 🔐 | Policy, role assignment, or guardrail |
  | ✨ | Model or deployment | 🌐 | URL or endpoint |
  | 🚀 | Gateway ready, deployment done, or app started | 🆔 | Resource or subscription ID |
  | ⏳ | Waiting or provisioning in the background | 📍 | Region |
  | 🔌 | Model provider, connector gateway, backend, or MCP server | 🤖 | Model or agent reply |
  | 🔖 | Alias | 🚦 | Expected 429, 403, or 400 from a policy |
  | 🔧 | MCP tools | 📊 | Metrics, logs, queries, or a listing |
  | 📂 | Folder or clone | 🔒 | Private networking or DNS |
  | 🚮 | Delete or purge | 📄 | File written |
  | 🚨 | An unexpected error | ✅ | Success or a summary |
  | 💡 | A tip | | |

  `npm run check` warns about any other emoji in a Bash or PowerShell block, and about a line that continues a quote
  or heredoc with a glob character after a URL. Keep this table and `SHELL_EMOJI` in `build.mjs` in step.

### Callouts and checkpoints

> [!TIP]

> `az aigateway model policy list -g "$RG" --gateway-name "$GATEWAY" --provider-name "$PROVIDER" -n "$MODEL"`

Kinds: `NOTE`, `TIP`, `IMPORTANT`, `WARNING`, `CAUTION`. A blockquote starting with **Checkpoint**,
**Verify**, or **Check your work** becomes a green checkpoint.

### Interactive widgets

`<!-- widget: name {"json":"config"} -->` mounts a simulator on the site (invisible on GitHub, so
never put essential instructions in a widget).

| Widget | Purpose | Config |
|---|---|---|
| `request-lifecycle` | Animated request through auth → policies → backend → telemetry, with failure toggles | `{"focus":"tokenLimit"}` optional |
| `token-limit` | Rolling-window token limit simulator with 429 and Retry-After | `{"limit":1000,"period":"minute"}` |
| `request-rate` | Calls-per-window simulator for tools | `{"calls":5,"window":30}` |
| `tool-patterns` | Try allow and block patterns against a tool catalog | `{"tools":["learn_search","…"],"allow":["*"],"block":["*delete*"]}` |
| `budget` | Cost-limit simulator with per-key overrides | `{"amount":5,"period":"day"}` |
| `alias-retarget` | Retarget an alias between backend models without client changes | none |
| `alias-routing` | Priority and weight routing across an alias's backend models, with presets and a 20-request run | `{"alias":"chat"}` optional |
| `stream-usage` | A streamed reply chunk by chunk, with and without `include_usage`, against a token limit that counts every stream | `{"limit":1000,"alias":"gpt-6-luna-stream"}` optional |
| `policy-layers` | Which gateway and asset policies apply to a request | none |

### Videos

`<!-- video: media/walkthrough.mp4 | Caption -->` embeds a narrated video. Put three files with the same
name in the lab's `media/` folder:

| File | Purpose |
|---|---|
| `walkthrough.mp4` | H.264 and AAC, 1920×1080, under about 40 MB, with the captions burned in |
| `walkthrough.vtt` | WebVTT captions file, linked from the GitHub view for download and translation |
| `walkthrough.jpg` | Poster, 16:9, with a play button drawn on it (GitHub shows it as a link) |

The site shows a player and a **Watch video** button in the lab header. The player has no browser full-screen
mode: Edge's scareware blocker scans full-screen pages and can flag narrated product UI as a scam, so
**Expand**, double-click, and <kbd>F</kbd> open an in-page theater view instead. Clicking the picture plays or
pauses, so the play button drawn on the poster works in every browser. GitHub can't play MP4s in a
README, so the GitHub view shows the poster linked to the site player, plus download and captions links.
Keep the video optional: every step it shows must also be written in the lab.

## Writing style

- Second person, present tense, active voice. Sentence-case headings. Short paragraphs.
- Lead with the outcome. Explain *why* before *how* in one or two sentences, then give exact steps.
- Use exact portal labels in bold. Never invent UI labels, CLI flags, or JSON fields. When automation for a
  feature isn't documented, give the portal path and say so.
- Every command must be copy-pasteable. Prefer environment variables set once at the top of a track.
- Bash first, PowerShell as an adjacent tab where it matters.
- Never list the AI Gateway regions, because they change. Link to
  [Find the available regions](SETUP.md#find-the-available-regions), and use `eastus2` as the example value.
- Don't describe AI Gateway as a preview service or as free. Mark a capability that's still emerging with
  `status: emerging`, and link to its release note.
- Always include clean-up instructions and point out billable resources.

## Infrastructure as code

- Bicep files live in the lab's `infra/` folder and must compile without warnings:
  `az bicep build --file infra/<file>.bicep --stdout > /dev/null`. Bicep has no types yet for
  `Microsoft.ApiManagement/aigateways` and `Microsoft.Web/connectorGateways`, so put `#disable-next-line BCP081` on
  the line before each of their `resource` declarations, including `existing` ones.
- Use API version `2025-09-01-preview` for `Microsoft.ApiManagement/*` resources.
- Gateways are the dedicated `Microsoft.ApiManagement/aigateways` type, never `Microsoft.ApiManagement/service`.
  Follow the product's [reference sample](https://github.com/Azure-Samples/simple-foundry-hosted-agent-python-aigateway/blob/main/infra/ai-gateway/main.bicep), as
  [lab 01's template](01-provision-gateway/infra/gateway.bicep) does: set `sku: { name: 'Consumption' }` (without it,
  the gateway is created in the `Premium` SKU) and no publisher properties, then create a
  `Microsoft.Web/connectorGateways` resource with the same name (API version `2026-05-01-preview`) that depends on
  the gateway. A subscription can have at most five gateways in each region.
  Gateway names have 24 characters or fewer, and the runtime URL is `https://` plus
  `properties.frontend.defaultHostname` (`<name>.<region>-01.ai.gateway.azure.com`).
- Policy `counterKey` values are arrays: `counterKey: [ 'identity' ]` or `[ 'ipAddress' ]`.
- CLI tracks use the `az aigateway` extension (1.0.0b15 or later, see
  [Install the aigateway extension](SETUP.md#install-the-aigateway-extension)) for gateways, providers, models,
  aliases, model policies (`model policy set-token-limit`, `set-content-safety`, `remove`), API keys (including
  `api-key regenerate --key-type secondary`), and MCP servers. Call ARM with `az rest` only for what the extension
  can't do yet: gateway and workspace policies, telemetry exporters, MCP versions, tool rules and `failureMode`,
  network settings after creation, API key `state`, and the connector gateway. Say why in one sentence. Set
  `GATEWAY_ID` with `az aigateway show`, plus `WS` (`https://management.azure.com$GATEWAY_ID/workspaces/default`)
  and `API` (`api-version=2025-09-01-preview`), only in tracks that still call `az rest`. Publish aliases with
  `model-alias set`, which creates the alias or updates it, so a step can run again. `--token-counter-key` takes one
  or more values (`Identity IPAddress`). `model-provider update --foundry` and `--custom` merge a partial JSON value
  into the provider's settings. `PATCH` and `--policies` replace whole arrays such as `properties.policies`, so
  read, edit, then write.
- Parameterize names and locations; default `location` to `resourceGroup().location` in resource-group-scoped
  modules.
- Mirror the structure of the existing labs: lab 06 for a Bicep + azd track (see [azd templates](#azd-templates)),
  lab 21 for an enterprise template with parameter files and a pipeline, and lab 16 for an azd project that deploys
  a hosted agent.
- Python hosted agents ship a pinned `requirements.txt`. Don't ship a `pyproject.toml` without its `uv.lock`, because
  the Foundry remote build then treats the project as Poetry and fails. Never commit lock files that point to a private
  package index.

## Runtime calls

- The model endpoint (`<gateway URL>/default/models/openai/v1`) accepts a runtime key in the `api-key` header, the
  same key as `Authorization: Bearer <key>`, or a Microsoft Entra token. With an OpenAI SDK, pass the key as the
  client's API key and add no `api-key` header: a request with both headers fails with `400` "Specify either an API
  key or an Authorization header, not both".
- The MCP endpoint (`<gateway URL>/default/toolservers/<name>/mcp`) reads keys only from the `api-key` header. A
  bearer token there must be a Microsoft Entra token.
- The gateway publishes federated tools as `<namespace>_<tool>`, with one underscore, for example
  `learn_microsoft_docs_search`.

## Notebooks

Some labs ship a Jupyter notebook, `NN-slug/NN-slug.ipynb`, that runs the lab end to end from Python. The build
finds it automatically: the lab page gets a **Notebook** button, and the GitHub header, the catalog, and the
**Run the notebooks** table link to it.

A notebook deploys the lab's own Bicep files, so the notebook and the Bicep track can't drift apart. It keeps its
cells short by importing [`shared/utils.py`](shared/utils.py):

- `lab = utils.Lab("NN-slug")` reads the `az login` sign-in and the shared defaults (resource group
  `rg-ai-gateway-labs`, gateway `aigw-labs-<6 characters of the SHA-1 of the subscription ID>`, region `eastus2`)
  that the `AIGW_*` environment variables override. It stops with a clear `❌` message when the gateway is missing.
- `lab.deploy("infra/limited-alias.bicep", **params)` runs `az deployment group create` and returns the template's
  outputs. Deploy the lab's resource-group-scoped modules, not the azd track's subscription-scoped `main.bicep`.
  When a step needs a resource that no lab template declares, add a small template to the lab's `infra/` folder
  (for example `11-entra-rbac/infra/role-assignment.bicep`) rather than writing ARM request bodies in the notebook.
- `lab.require`, `lab.delete`, `lab.api_key`, `utils.retry`, `utils.wait_for_status`, and the `mcp_*` helpers cover
  the reads, clean-up, and waits around a deployment. Put a new helper in `utils.py` when more than one notebook
  needs it.

Follow the structure of the existing notebooks:

1. A Markdown intro: the H1, a one-line flow of what the notebook builds, a table of the resources it uses
   (including the Bicep files and `utils.py`), prerequisites (`az login`, Python 3.10 or later), and a note to
   select **Run All**.
2. A `%pip install` cell with only the packages the notebook needs.
3. **0. Initialize variables**: import `utils` from `../shared`, create the `Lab`, and set the lab's own names.
4. Numbered steps that mirror the lab's sections. Each step has a short Markdown explanation and a code cell that
   deploys or reuses resources, waits for the gateway to apply them, and checks the result with `assert`.
5. **Clean up** (delete only what the notebook created), **Troubleshooting**, and **Next steps**. The
   Troubleshooting cell lists the errors that are specific to the notebook, then links to the lab's section on the
   [Troubleshooting page](#the-troubleshooting-page).

Never print or save keys or tokens. Run the notebook from its lab folder, start to finish, against a real
subscription before you commit it, then clear all outputs (`jupyter nbconvert --clear-output --inplace <file>`).

## Release notes

[`RELEASE-NOTES.md`](RELEASE-NOTES.md) is the source of truth for the labs release notes. The build renders it
at `/release-notes/` on the site, links it from the top navigation and the footer, and shows the newest entry
as a pill on the home page. On GitHub it renders as is.

- Add one `## <Month D, YYYY>` section per product release, newest first, with an `### <product title>` heading
  that matches the product's changelog title and a link to `https://ai.gateway.azure.com/docs/releases/<YYYY-MM-DD>`.
  Then add the date to the `**Releases:**` jump line at the top (it ends with `<!-- gh -->`, so the site, which has
  its own release list, hides it).
- Under it, a table maps each product change to the lab that practices it: `| In the product | Practice it in
  the labs | Status |`, with 🆕 for a new lab, ✏️ for an updated lab, ✅ for a lab that already covered it, and
  ➖ for a change no lab covers yet. Link to the lab section (`NN-slug/README.md#anchor`) that practices it.
- List changes to the labs under `#### Labs changes` in the newest release section at the time you make them,
  each starting with its date in bold, newest first.
- `npm run releases` reads the product changelog from the docs site and flags the releases the file doesn't
  mention yet, with the full text of each one's changelog entry and release page (including screenshot URLs).
  `-- --check` exits with code 1 when one is missing, `-- --page /docs/<page>` prints any product docs page,
  `-- --pages` lists them, and `-- --save-bundle <file>` saves the docs bundle so you can search it for exact
  portal labels. The docs site is a single-page app, so a plain fetch of a docs URL returns no content.
